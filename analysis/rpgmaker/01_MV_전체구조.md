> 출처: RPG Maker MV corescript (MIT, KADOKAWA/YOJI OJIMA), 분석일 2026-10-26
>
> 분석 대상: `engine-tool-refs/rpgmaker-mv-corescript/js` (헤더 표기 `rpg_core.js v1.6.1 (community-1.3b)`, 커뮤니티 유지보수판)
> 목적: Beyond Records 전용 툴(카드 수집형 턴제 RPG + 비주얼노벨식 스토리) 설계 참고. 타일맵·필드 이동은 제외 대상이므로 간단히만 다룬다.

## 0. 한 줄 요약

MV 런타임은 **"전역 정적 매니저 + 전역 게임 상태 객체($game*) + 전역 DB 객체($data*) + Scene 스택 + PIXI 기반 Sprite/Window"** 구조다. 모든 클래스가 `window` 전역에 올라가고, 확장은 플러그인이 **프로토타입 메서드를 덮어써서** 한다. 빠르게 만들고 쉽게 뜯어고치기엔 좋지만, 경계(모듈·타입·의존 방향)가 거의 없다.

## 1. 계층 구조와 책임

`index.html`이 `<script>`를 순서대로 로드한다 (추정: 표준 프로젝트 템플릿 기준 순서는 libs → rpg_core → rpg_managers → rpg_objects → rpg_scenes → rpg_sprites → rpg_windows → plugins.js → main.js). 각 폴더는 원래 하나의 `.js` 파일(rpg_core.js 등)로 합쳐 배포되는 단위이며, 이 저장소에서는 클래스별 파일로 쪼개져 있다.

| 계층 | 대표 클래스 | 책임 | 비고 |
|---|---|---|---|
| **libs** | pixi.js(v4), pixi-tilemap, pixi-picture, lz-string, fpsmeter | 렌더링, 압축 | 외부 라이브러리 |
| **rpg_core** | `Graphics`, `Bitmap`, `Sprite`, `Window`, `WindowLayer`, `Stage`, `Tilemap`, `WebAudio`, `Html5Audio`, `Input`, `TouchInput`, `JsonEx`, `Utils`, `ImageCache`, `RequestQueue`, `Decrypter`, `ResourceHandler` | 게임 장르와 무관한 **엔진 기반**: 캔버스·렌더러, 비트맵 그리기, 오디오 재생, 입력, 직렬화 | 원칙적으로 게임 규칙을 모름 (`$game*` 참조 없음 — grep 확인) |
| **rpg_managers** | `DataManager`, `SceneManager`, `BattleManager`, `StorageManager`, `ImageManager`, `AudioManager`, `SoundManager`, `ConfigManager`, `TextManager`, `PluginManager` | **정적(static) 싱글톤 서비스**. 로딩, 씬 전환, 전투 진행, 저장 | 모두 `function X(){ throw 'static class' }` 패턴 |
| **rpg_objects** | `Game_Temp/System/Screen/Timer/Message/Switches/Variables/SelfSwitches/Actors/Party/Troop/Map/Player`, `Game_BattlerBase → Game_Battler → Game_Actor/Game_Enemy`, `Game_Action`, `Game_ActionResult`, `Game_Item`, `Game_Interpreter`, `Game_Picture` … | **게임 상태(Model)와 규칙**. 세이브 대상 | 화면을 직접 그리지 않음. 대신 "연출 요청 플래그"를 남긴다 (5절) |
| **rpg_scenes** | `Scene_Base`(extends `Stage`) → `Scene_Boot/Title/Map/Menu/Battle/Shop/Save/Load/...` | **화면 단위 컨트롤러**. 자신이 쓸 Window·Spriteset을 만들고 연결 | 입력 → 윈도우 핸들러 → 게임 객체 호출 |
| **rpg_sprites** | `Sprite_Base`, `Sprite_Battler/Actor/Enemy`, `Sprite_Animation`, `Sprite_Damage`, `Sprite_Picture`, `Spriteset_Base/Map/Battle` | **게임 객체를 관찰해 그리는 View** | 매 프레임 Game 객체를 폴링 |
| **rpg_windows** | `Window_Base` → `Window_Selectable` → `Window_Command` → 각종 메뉴/전투/메시지 창 | **UI 위젯**. 텍스트·아이콘 그리기, 커서·선택, 메시지 출력 | 게임 객체를 직접 읽음 |

### 1.1 상속 축 (게임 로직 쪽)

- `Game_BattlerBase` (`rpg_objects/Game_BattlerBase.js`): 능력치 계산, 특성(Trait) 조회, 상태·버프 저장, 스킬 사용 가능 여부.
- `Game_Battler` (`rpg_objects/Game_Battler.js`): 행동(Action) 목록, 상태 부여/해제 처리, 턴 시작·종료 처리, 재생/슬립 데미지, 연출 요청 큐.
- `Game_Actor` / `Game_Enemy`: "특성의 출처"와 "기본 능력치의 출처"만 다르게 오버라이드. 이 분리 방식이 MV 설계에서 가장 재사용 가치가 큰 부분이다(02 문서 참고).
- `Game_Unit` → `Game_Party` / `Game_Troop`: 아군·적군 집단. 대상 선택, 전멸 판정.

### 1.2 상속 축 (UI 쪽)

`PIXI.Container` → `Stage` → `Scene_Base`, `PIXI.Container` → `Window`(core) → `Window_Base`(텍스트·제어문자·아이콘·게이지 그리기) → `Window_Selectable`(커서, 스크롤, 터치 hitTest, OK/Cancel 핸들러) → `Window_Command`(심볼 기반 명령 목록) → 개별 창.

`Window_Command`의 **"심볼 + 핸들러" 패턴**(`addCommand(name, symbol)` / `setHandler(symbol, fn)`)은 씬이 창에 콜백을 꽂는 방식으로, 단순하지만 UI와 씬 로직을 느슨하게 연결하는 좋은 예다.

## 2. 의존 방향

```
main.js
  └→ PluginManager.setup($plugins)   (플러그인 <script> 삽입)
  └→ SceneManager.run(Scene_Boot)

rpg_core  ←────────────── 모든 계층이 사용 (core는 상위를 모름: 원칙상 단방향)
rpg_managers ⇄ rpg_objects   (양방향!)
   DataManager가 Game_* 를 new 하고, Game_* 는 $data*, SceneManager, BattleManager 를 호출
rpg_scenes  → managers, objects, sprites, windows
rpg_sprites → objects(읽기), core
rpg_windows → objects(읽기), managers(TextManager, ImageManager, SoundManager), core
```

관찰된 역방향/교차 의존 예:

- **objects → scenes**: `Game_Interpreter`가 `SceneManager.push(Scene_Battle)`, `Scene_Shop`, `Scene_Menu`, `Scene_Save`, `Scene_Gameover`를 직접 호출 (`rpg_objects/Game_Interpreter.js:command301/302/303/351/352/353/354`).
- **managers → windows/sprites**: `BattleManager.isBusy`가 `this._logWindow.isBusy()`와 `this._spriteset.isBusy()`를 본다 (`rpg_managers/BattleManager.js:isBusy`). 즉 **전투 규칙 진행 속도가 UI 창(Window_BattleLog)의 연출 큐에 묶여 있다.** 로직만 떼어 시뮬레이션하기 어렵다.
- **managers → scenes**: `DataManager.onLoad`가 `Scene_Boot.loadSystemImages()`를 호출.
- 모든 계층이 `$gameParty`, `$dataSkills` 같은 전역을 자유롭게 읽는다. 의존이 import 문에 드러나지 않으므로 "누가 무엇을 쓰는지"는 grep으로만 알 수 있다.

**결론**: 폴더 이름은 계층처럼 보이지만 실제 강제되는 의존 규칙은 "core는 게임을 모른다" 하나뿐이다.

## 3. 게임 루프와 Scene 전환

### 3.1 부트 순서

1. `main.js`: `PluginManager.setup($plugins)` → `window.onload`에서 `SceneManager.run(Scene_Boot)`.
2. `SceneManager.initialize` (`rpg_managers/SceneManager.js:initialize`): Graphics(캔버스·렌더러) → 파일 접근 검사 → WebAudio → Input/TouchInput → NW.js 메뉴 → **플러그인 로드 오류 검사** → 전역 에러 핸들러.
3. `Scene_Boot.create`: `DataManager.loadDatabase()`, `ConfigManager.load()`, 시스템 이미지 예약.
4. `Scene_Boot.isReady`: 이미지 캐시 준비 + DB 전부 로드 + 폰트 로드 완료까지 대기.
5. `Scene_Boot.start`: 일반 실행이면 `DataManager.setupNewGame()` 후 `Scene_Title`로. 쿼리 옵션 `btest`(전투 테스트), `etest`(이벤트 테스트)면 바로 `Scene_Battle`/`Scene_Map`로. → **에디터의 "테스트 플레이"가 같은 런타임을 URL 옵션으로 띄우는 방식.** 우리 툴의 "에디터 미리보기 = 실제 런타임" 목표와 같은 발상.

### 3.2 프레임 루프 (`SceneManager.update` / `updateMain`)

- `requestAnimationFrame`으로 돈다.
- **고정 시간 간격(1/60초) 누산기 방식**: 실제 경과 시간을 `_accumulator`에 더하고, 1/60초 단위로 `updateInputData → changeScene → updateScene`을 반복한 뒤 한 번 `renderScene`. 프레임 간 최대 0.25초로 잘라 "죽음의 나선"을 막는다. 모바일 Safari만 예외적으로 프레임당 1회 갱신.
- 모든 시간 단위가 **프레임 수**(60fps 가정)다. 페이드 24프레임, 메시지 대기 15/60프레임, 터치 롱프레스 24프레임 등.

### 3.3 Scene 생명주기와 전환

| 단계 | 호출 | 의미 |
|---|---|---|
| 요청 | `SceneManager.goto(Cls)` / `push(Cls)` / `pop()` | 다음 씬 **인스턴스를 즉시 생성**해 `_nextScene`에 보관, 현재 씬 `stop()` |
| 인자 전달 | `SceneManager.prepareNextScene(...)` → 다음 씬의 `prepare(...)` | 생성자가 아닌 별도 메서드로 매개변수 전달 |
| 교체 | `changeScene` (현재 씬이 `isBusy()`=페이드 중이 아닐 때) | 이전 씬 `terminate()` + 이미지 예약 해제 → 새 씬 이미지 예약 등록 + `create()` |
| 대기 | `updateScene`에서 `isReady()`가 true가 될 때까지 로딩 화면 | 리소스 로드 완료 대기 |
| 시작 | `start()` 1회 | 페이드 인, BGM 등 |
| 갱신 | 매 고정 프레임 `update()` | 자식들의 `update()` 재귀 호출 |

- **씬 스택**: `push`는 현재 씬의 **클래스(생성자)** 만 스택에 저장한다. `pop` 시 그 클래스를 **새로 생성**한다. 즉 메뉴에서 돌아오면 이전 씬은 다시 만들어지며, 상태는 씬이 아니라 `$game*` 전역에 있으므로 문제없다. → **"상태는 씬 밖(게임 객체)에, 씬은 언제든 재생성 가능한 뷰"** 라는 원칙. 우리 툴에도 그대로 가져갈 만하다.
- 배경 블러: 메뉴로 들어갈 때 `SceneManager.snapForBackground()`로 현재 화면을 캡처·블러해 다음 씬 배경으로 쓴다.
- 이미지 메모리: 씬마다 `_imageReservationId`를 가지고 `ImageManager`의 캐시 예약을 씬 수명에 묶는다 (`rpg_scenes/Scene_Base.js:attachReservation/detachReservation`). 캐시 상한은 `ImageCache.limit = 10,000,000` 픽셀이며 예약되지 않은 오래된 이미지부터 버린다 (`rpg_core/ImageCache.js`).

### 3.4 전투 진행 (`BattleManager`)

- 문자열 상태 머신: `init → start → input → turn → (action ↔ turn) → turnEnd → … → aborting/battleEnd`.
- 턴 순서: 모든 전투원의 `Game_Action.speed`(민첩 + 난수 + 스킬 속도 보정)를 계산해 내림차순 정렬 (`BattleManager.makeActionOrders`).
- 각 행동: `startAction`(대상 결정, 비용 지불, 공통이벤트 예약) → 대상마다 `invokeAction` (반격 확률 `cnt`, 마법반사 확률 `mrf`, 아니면 `Game_Action.apply`).
- `BattleManager.update`는 `$gameMessage`, 스프라이트셋, 로그 창이 하나라도 바쁘면 진행을 멈춘다. → **로직과 연출이 같은 틱에서 서로를 기다리는 구조.**

### 3.5 스토리 연출 (`Game_Interpreter`) — VN 기능과 직결

- 이벤트는 `{code, indent, parameters}` 명령의 **평면 배열**이다. 분기·루프 구조는 `indent` 값과 분기 코드(예: 111 조건분기, 411 Else, 112 Loop / 413 Repeat Above)로 표현한다. 조건이 거짓이면 `skipBranch`가 현재보다 indent가 깊은 명령을 건너뛰는 방식이라, 블록 범위가 **들여쓰기 숫자에만** 의존한다 (`rpg_objects/Game_Interpreter.js:skipBranch`).
- 실행은 `executeCommand`가 `'command' + code` 이름의 메서드를 찾아 호출하는 **동적 디스패치**. 메서드가 `false`를 반환하면 다음 프레임에 재시도(=대기). 대사 표시(101), 선택지(102), 대기(230), 그림 표시(231~235), BGM(241~), 화면 페이드/흔들기(221~225) 등이 모두 이 방식이다.
- 확장점: 355 Script(임의 JS eval), 356 Plugin Command(`pluginCommand(command, args)`를 플러그인이 덮어씀).
- 대사 창(`rpg_windows/Window_Message.js`)은 제어 문자(`\V[n]` 변수, `\N[n]` 이름, `\.` `\|` 대기, `\!` 입력 대기, `\>` `\<` 즉시표시, `\^` 자동 넘김 등)를 한 글자씩 해석한다.
- 그림(CG) 슬롯은 `Game_Screen.maxPictures = 100`개의 번호 슬롯 방식.
- **평가**: "명령 배열 + 인터프리터"는 에디터에서 리스트 UI로 편집하기 쉽고, 저장 중에도 `_index`만 있으면 이어서 실행 가능하다는 큰 장점이 있다. 반면 명령 코드가 숫자라 사람이 읽기 어렵고, 파라미터가 위치 기반 배열이라 스키마가 코드 안에만 있다.

## 4. 데이터 로딩 (DataManager)

- DB 파일 목록이 `DataManager._databaseFiles`에 하드코딩: Actors, Classes, Skills, Items, Weapons, Armors, Enemies, Troops, States, Animations, Tilesets, CommonEvents, System, MapInfos. 각 파일은 XHR로 받아 **`window['$dataActors']` 같은 전역 변수에 그대로 대입**한다 (`DataManager.loadDataFile`).
- 맵은 필요할 때 `Map%03d.json`을 `$dataMap`에 로드 (`DataManager.loadMapData`).
- 로드 직후 `DataManager.onLoad` → 각 레코드의 `note` 문자열을 파싱해 `meta` 객체를 만든다 (`DataManager.extractMetadata`: `<태그>` → `meta.태그 = true`, `<태그:값>` → `meta.태그 = "값"` 문자열). 상세는 02 문서.
- 로딩 완료 판정은 폴링: `isDatabaseLoaded`가 모든 전역이 null이 아닌지 확인. 실패 URL은 `_errorUrl`에 기록 후 다음 확인 때 throw.
- 테스트 모드면 `Test_` 접두 파일을 읽는다(에디터가 테스트용 스냅샷을 따로 쓰는 방식).
- **런타임은 DB를 읽기 전용으로 취급**한다(관례). 단, 객체가 그냥 가변 JS 객체라서 코드가 실수로 수정해도 막을 방법이 없다.
- 배열 인덱스 = ID. 모든 DB 배열의 `[0]`은 `null`이며 ID 1부터 시작 (추정: 에디터가 생성하는 JSON 형태 기준. `DataManager.onLoad`가 `data && ...`로 null을 건너뛰는 것으로 뒷받침됨).

## 5. 세이브 (StorageManager, JsonEx)

### 5.1 무엇을 저장하나

`DataManager.makeSaveContents`: `$gameSystem, $gameScreen, $gameTimer, $gameSwitches, $gameVariables, $gameSelfSwitches, $gameActors, $gameParty, $gameMap, $gamePlayer`. (`$gameTemp`, `$gameMessage`, `$gameTroop`은 제외 — 휘발성)

핵심 원칙: **세이브에는 DB 객체를 넣지 않고 ID만 넣는다.** `Game_Item`이 `{_dataClass:'skill', _itemId:3}`처럼 종류+ID만 들고 있다가 `object()` 호출 때 `$dataSkills[3]`을 찾아오는 이유가 이것이다 (`rpg_objects/Game_Item.js` 머리 주석). 상태도 `_states`는 ID 배열, 인벤토리는 `{itemId: 개수}` 맵.

→ 장점: DB를 패치(밸런스 수정)해도 기존 세이브에 즉시 반영. 세이브 용량이 작다.
→ 주의: DB에서 ID를 지우거나 재배치하면 세이브가 깨진다. **ID는 영구 불변**이어야 한다.

### 5.2 JsonEx — 클래스 복원 직렬화

- `JsonEx.stringify`: 객체마다 `@c`(객체 ID)를 붙이고, `Object`/`Array`가 아니면 `@`에 **생성자 이름 문자열**(예: `"Game_Actor"`)을 기록. 이미 나온 객체는 `{"@r": id}` 참조로 바꿔 순환·공유 참조를 보존. 배열은 `{"@c", "@a"}`로 감싼다.
- `JsonEx.parse`: `window[생성자이름].prototype`으로 프로토타입을 되살린다 (`JsonEx._decode`, `_resetPrototype`). 생성자는 호출하지 않는다.
- 최대 깊이 100, 세이브 JSON이 20만 자를 넘으면 경고.
- **약점**: 클래스 이름이 저장 포맷의 일부가 된다. 클래스 이름 변경·삭제, 전역에 없는 클래스(모듈 스코프, 번들러 난독화)면 복원이 조용히 실패한다(일반 객체로 남음). 필드 추가 시 구버전 세이브는 그 필드가 `undefined` → 플러그인들이 "로드 후 누락 필드 초기화" 코드를 각자 넣는 관행이 생긴다 (추정). **스키마 버전/마이그레이션 개념이 없다.**

### 5.3 저장 매체

- `StorageManager.isLocalMode()` = NW.js인지 여부. NW.js면 `save/fileN.rpgsave` 파일(fs), 브라우저/모바일 웹뷰면 `localStorage` 키(`RPG File1`, `RPG Global`, `RPG Config`).
- 모두 **LZString Base64 압축** 후 저장.
- 슬롯 0 = 전역 정보(`global`: 슬롯별 제목·얼굴·플레이시간·타임스탬프 → 세이브 목록 화면용), 음수 = 설정(config), 1~20 = 게임 슬롯 (`DataManager.maxSavefiles = 20`).
- 안전장치: 저장 전 기존 파일을 `.bak`/`...bak` 키로 백업, 실패하면 복원 (`DataManager.saveGame`, `StorageManager.backup/restoreBackup`). 자동 저장은 `_autoSaveFileId`로 커뮤니티판에서 추가된 것.
- 동기 API(`fs.writeFileSync`, `localStorage`)만 사용 → 큰 세이브에서 프레임 끊김 가능, Capacitor 등 비동기 저장소에 바로 못 붙음.

## 6. 플러그인 시스템 (PluginManager)

### 6.1 로딩

- 에디터가 `js/plugins.js`에 `var $plugins = [{name, status, description, parameters}, ...]`를 생성한다 (추정: plugins.js는 이 저장소에 없음. `PluginManager.setup`의 사용 형태로 판단).
- `PluginManager.setup`: `status`가 true인 플러그인마다 파라미터를 저장하고 `<script src="js/plugins/이름.js" async=false>`를 body에 붙인다. `async=false`라서 **목록 순서대로 실행**된다. 이 순서가 곧 덮어쓰기 우선순위다.
- 로드 실패 URL은 `_errorUrls`에 쌓였다가 `SceneManager.initialize → checkPluginErrors`에서 throw.
- 코어 전체가 플러그인보다 먼저 로드되므로 플러그인은 모든 전역 클래스에 접근 가능하다.

### 6.2 파라미터

- `PluginManager.parameters('플러그인명')` → `{키: 문자열}`. **모든 값이 문자열**이라 플러그인이 `Number(...)`, `JSON.parse(...)`로 직접 변환한다.
- 파라미터의 이름·타입·기본값·설명은 플러그인 파일 상단 주석의 `@param`, `@type`, `@default` 같은 어노테이션으로 선언하고, **에디터가 그 주석을 파싱해 설정 UI를 자동 생성**한다 (추정: 런타임 코드에는 파서가 없음. 에디터 측 기능).

### 6.3 확장 방식 — 프로토타입 덮어쓰기(monkey patch)

정형화된 훅/이벤트 시스템이 없다. 플러그인은 대체로 다음 패턴을 쓴다 (커뮤니티 관행, 코어 코드가 강제하는 것은 아님):

1. 기존 메서드를 변수에 보관 (`var _old = Game_Action.prototype.apply;`)
2. 같은 이름으로 새 함수를 대입하고 내부에서 `_old.call(this, ...)`를 호출 (**별칭/체이닝**)
3. 혹은 원본을 호출하지 않고 **완전히 교체**

코어 쪽도 이를 전제로 설계됐다: 메서드를 매우 잘게 쪼개 둔 이유(예: `makeDamageValue` 안에서 `applyCritical`, `applyVariance`, `applyGuard`를 각각 별도 메서드로 둔 것, `Game_Interpreter.pluginCommand`가 빈 함수인 것)는 **"덮어쓰기 좋은 지점"을 많이 만들기 위해서**로 보인다 (추정, 구조에서 유추).

### 6.4 평가

| 장점 | 약점 |
|---|---|
| 진입 장벽 0: JS 파일 하나 넣으면 어떤 동작이든 바꿀 수 있다 | **충돌**: 두 플러그인이 같은 메서드를 "완전 교체"하면 나중 것만 살아남는다. 순서 바꾸면 결과가 달라진다 |
| 코어 수정 없이 거의 모든 것을 확장 가능 | 체이닝해도 "원본 호출 전/후" 위치에 따라 의미가 달라져 조합 결과 예측이 어렵다 |
| 에디터가 주석에서 파라미터 UI를 자동 생성 | 의존성·버전·로드 순서 선언이 없다 (커뮤니티 플러그인이 주석 관례로 해결) |
| | 모든 파라미터가 문자열, 타입 검증 없음 |
| | 덮어쓴 메서드 이름이 사실상 공개 API가 돼서 **코어 업데이트가 어렵다**(내부 메서드명 하나 바꿔도 플러그인이 깨짐) |
| | 디버깅 시 실제 실행 함수가 어디서 왔는지 추적하기 어렵다 |

## 7. 모바일·터치 대응

### 7.1 해상도·스케일 (Graphics)

- 논리 해상도 고정: `SceneManager._screenWidth/_screenHeight = 816 × 624`, UI 박스(`boxWidth/boxHeight`)도 같은 값. 모든 좌표는 이 논리 좌표로 처리.
- `Graphics._updateRealScale`: 스트레치 모드면 `min(창너비/논리너비, 창높이/논리높이)`로 **비율 유지 확대(레터박스)**. 스트레치 기본값은 NW.js 또는 모바일일 때 켜짐 (`Graphics._defaultStretchMode`). 캔버스는 CSS로 화면 중앙 정렬 (`_centerElement`).
- 해상도 변경은 플러그인이나 코드 수정으로 `_screenWidth` 등을 바꿔야 한다 (에디터 UI에는 없음, 추정: MV 기준). 세로 화면/안전 영역(노치) 개념은 없다.
- 렌더러는 PIXI WebGL/Canvas 자동 선택(`preferableRendererType`). `shouldUseCanvasRenderer`가 모바일이면 true를 반환하도록 정의돼 있으나 기본 흐름에서 호출되지 않는다 (확인 범위 내).

### 7.2 입력 (TouchInput)

- 마우스와 터치를 **하나의 "포인터" 추상**으로 통합: `isTriggered`(눌림 순간), `isPressed`, `isRepeated`(24프레임 후 6프레임마다 반복), `isLongPressed`, `isReleased`, `isMoved`, `isCancelled`.
- 페이지 좌표 → 캔버스 논리 좌표 변환은 `Graphics.pageToCanvasX/Y`.
- **두 손가락 터치 = 취소(우클릭)** 로 처리 (`TouchInput._onTouchStart`). 멀티터치·핀치·스와이프 제스처는 없다. 휠 값만 누적.
- 이벤트는 브라우저 콜백에서 `_events`에 쌓아 두고 `TouchInput.update`에서 프레임 단위 스냅샷으로 옮긴다 → 로직은 항상 "이번 프레임에 눌렸나"만 본다. 게임 루프 방식 입력 처리의 정석.
- 창 터치: `Window_Selectable.processTouch` → `hitTest`로 항목 인덱스 계산. **이미 선택된 항목을 다시 탭하면 결정**(첫 탭=선택, 두 번째 탭=확정). 창 밖 영역에서 터치 취소 처리. 스크롤은 창 위/아래 끝을 누르고 있으면 진행.
- `Sprite_Button`은 존재하지만 코어에서는 숫자 입력 창(`Window_NumberInput`, `Window_ShopNumber`)에서만 쓴다. 터치 전용 UI(뒤로가기 버튼 등)는 기본 제공되지 않는다 (MV의 유명한 모바일 UX 약점; MZ에서 보강됨 — 추정, 외부 지식).

### 7.3 기타 모바일 대응

- iOS 오디오/비디오 잠금 해제: 첫 터치 시 비디오 재생 시도(`Graphics._onTouchEnd`), WebAudio 컨텍스트 resume 핸들러(`WebAudio._setupEventHandlers`).
- 모바일 Safari는 고정 스텝 루프를 쓰지 않는 분기 존재.
- `Utils.isMobileDevice`는 UserAgent 정규식 판별.

## 8. 장점 / 약점 종합 평가

### 8.1 장점 (가져올 것)

1. **Model / View 분리가 "대략" 지켜진다.** 게임 상태는 `Game_*`에만 있고, Sprite는 매 프레임 Game 객체를 읽어 그린다. 연출이 필요하면 Game 객체가 요청 큐(`Game_Battler.startAnimation`→`_animations`, `startDamagePopup`, `requestEffect`)를 남기고 Sprite가 꺼내 간다(`Sprite_Battler.updateAnimation`, `Sprite_Enemy`). → 로직이 그리기 코드를 직접 호출하지 않는다.
2. **세이브 = 상태 객체 + ID 참조.** DB를 세이브에 넣지 않는 원칙이 깔끔하다.
3. **씬은 재생성 가능한 뷰.** 씬 스택이 클래스만 저장해도 되는 이유.
4. **데이터 주도(Data-driven).** 스킬·장비·상태 효과가 코드가 아니라 JSON의 Trait/Effect 배열로 정의됨 (02 문서 핵심).
5. **잘게 쪼갠 메서드** → 오버라이드 지점이 많아 확장이 쉽다.
6. **고정 시간 스텝 루프 + 프레임 스냅샷 입력**: 결정론적 업데이트에 유리.
7. **에디터 테스트가 같은 런타임을 옵션으로 실행**(`btest`, `etest`, `Test_*.json`).
8. 씬 단위 이미지 예약/해제로 모바일 메모리 관리.

### 8.2 약점 (피할 것)

1. **전역 객체 남용**: `$data*` 15개, `$game*` 14개, 모든 클래스·매니저가 `window` 전역. 테스트에서 격리 불가, 두 개의 게임 상태를 동시에 띄우는 것(예: 에디터에서 전투 시뮬레이션 여러 개 병렬)이 불가능.
2. **프로토타입 덮어쓰기 기반 확장**: 충돌, 순서 의존, 코어 업데이트 곤란 (6.4).
3. **로직이 UI에 묶임**: `BattleManager.isBusy`가 로그 창·스프라이트셋을 기다림. 전투 로직만 headless로 돌려 밸런스 시뮬레이션하려면 대수술 필요.
4. **정적 매니저 = 싱글톤**: `BattleManager`가 전투 상태를 정적 필드에 보관 → 동시에 전투 2개 불가, 테스트 어려움.
5. **타입·스키마 부재**: DB 필드는 `json_docs.js`의 주석 문서뿐이고, 명령 파라미터·코드 의미는 코드 안 switch문에만 있다. 매직 넘버(데미지 타입 1~6, 범위 1~11 등)가 곳곳에 하드코딩.
6. **문자열 eval**: 데미지 공식(`Game_Action.evalDamageFormula`), 스크립트 명령(355), 조건 분기 스크립트 → 보안·성능·오류 은폐(예외 시 0 반환) 문제.
7. **세이브 포맷이 클래스 이름에 의존, 마이그레이션 없음.**
8. **성능**: 특성 조회 때마다 모든 특성 객체 배열을 새로 concat·filter (`Game_BattlerBase.allTraits`) — 캐시 없음. 능력치 하나 읽을 때마다 반복된다.
9. **프레임 기반 시간**: 60fps 가정. 고주사율 기기에서는 누산기로 보정되지만, 모든 연출 시간이 "프레임 수"라 기획 데이터가 직관적이지 않다.
10. **모바일 UX 기본 지원 부족**: 고정 가로 해상도, 제스처 없음, 터치 전용 버튼 부족, 동기 저장소.
11. **ID = 배열 인덱스**: 삭제/재정렬에 취약, 여러 사람이(또는 여러 브랜치에서) 데이터를 동시에 추가하면 ID 충돌.

## 9. Beyond Records 툴 설계에 주는 시사점 (요약)

| MV 구조 | 우리 툴 제안 |
|---|---|
| core / managers / objects / scenes / sprites / windows | 계층은 유지하되 **`logic`(순수 TS, DOM·렌더러 의존 금지) / `runtime-view` / `editor`** 로 경계를 강제. 전투 로직은 `logic`에만 두고 연출은 이벤트 로그를 받아 재생 |
| `$game*` 전역 | `GameState` 객체 하나를 명시적으로 주입 (DI 또는 컨텍스트). 여러 인스턴스 가능하게 → 에디터에서 병렬 전투 시뮬레이션 |
| `BattleManager`가 로그 창을 기다림 | 로직은 한 번에 끝까지 계산해 **이벤트 목록**(`[{type:'damage', target, value}, ...]`)을 반환, 뷰가 그것을 재생. 로직 ↔ 연출 완전 분리 |
| JsonEx(클래스명 기반 복원) | 세이브는 **순수 데이터(plain JSON) + `saveVersion` + 마이그레이션 함수 체인**. 클래스 인스턴스는 로드 후 팩토리로 재구성 |
| ID = 배열 인덱스 | **문자열 안정 ID**(`card_ariel_001`) 또는 UUID + 정렬용 필드 분리 |
| 프로토타입 덮어쓰기 플러그인 | 1인 전용 툴이므로 플러그인 시스템 자체가 불필요할 가능성이 큼. 필요하면 **명시적 훅/레지스트리**(효과 코드 → 핸들러 등록 테이블)로 |
| `Game_Interpreter` 명령 배열 | VN 스크립트에 **그대로 차용할 가치 높음**: 명령 리스트 + 프로그램 카운터 + "false면 대기" 규칙. 단 코드 숫자 대신 `type: 'showText'` 문자열, 파라미터는 이름 있는 객체로 |
| 816×624 고정 + 레터박스 | 세로/가로 기준 해상도 선택 + 안전 영역 + 앵커 기반 UI 배치 |
| TouchInput 포인터 통합 + 프레임 스냅샷 | 개념은 차용, 스와이프·롱프레스·드래그(카드 끌기) 제스처 추가 |
| 씬 단위 이미지 예약 | 차용 (에피소드 단위 CG/BGM 프리로드 + 해제) |
