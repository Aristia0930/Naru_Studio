# RPG Maker MV 데이터베이스 구조 분석

> 출처: RPG Maker MV corescript (MIT, KADOKAWA/YOJI OJIMA), 분석일 2026-10-26
>
> 분석 대상: `engine-tool-refs/rpgmaker-mv-corescript/js` — 스키마 문서 `json_docs.js`(YUIDoc 주석으로 된 JSON 구조 설명, 실행 코드 없음)와 실제 사용 코드(`rpg_objects/*`, `rpg_managers/DataManager.js`)를 대조했다.
> 표기: 위치는 `폴더/파일:함수`. 코드에서 직접 확인하지 못한 내용은 **(추정)**.
> 주의: `json_docs.js`는 일부 필드를 빠뜨린다(예: System의 `encryptionKey`, `hasEncryptedImages/Audio`는 코드에서만 등장). 숫자 코드의 의미(범위·데미지 타입 등)는 json_docs에 없고 코드의 switch/배열 비교에서 역추적했다.

## 0. 공통 규칙

| 규칙 | 내용 | 근거 |
|---|---|---|
| 파일 = 배열 | `Actors.json` 등은 `[null, {id:1,...}, {id:2,...}]`. **배열 인덱스 = id** | `$dataSkills[id]` 형태 접근 전반, `Game_Item.object` |
| 0번은 null | ID 1부터. "0 = 없음"으로 쓰인다(예: `classId`, `animationId`, 장비 슬롯 0) | `DataManager.onLoad`가 null 건너뜀 (0번 null은 추정) |
| 예외 | `System.json`은 단일 객체, `MapInfos.json`은 맵 트리, `MapXXX.json`은 맵 하나 | `DataManager._databaseFiles` |
| `note` | 모든 주요 레코드에 자유 텍스트 메모 → 로드 시 `meta` 객체로 파싱 | `DataManager.extractMetadata` (5절) |
| 이름 목록 | 속성·스킬타입·무기타입·방어구타입·장비타입·스위치·변수의 **이름**은 System.json의 문자열 배열. 다른 데이터는 이 배열의 **인덱스**를 참조 | `$dataSystem.elements` 등 |
| 숫자 코드 | 범위·데미지 타입·특성 코드 등 열거형은 전부 정수 | 3·4절 |
| 능력치 ID | 0 최대HP, 1 최대MP, 2 공격력, 3 방어력, 4 마법공격, 5 마법방어, 6 민첩, 7 운 | `Game_BattlerBase`의 `mhp…luk` 게터 |

## 1. 파일별 구조와 역할

### 1.1 Actors.json — 캐릭터(개체 정의)
- `id, name, nickname, profile, note`
- `classId`: 소속 직업 → 능력치 성장·습득 스킬은 직업에서 온다
- `initialLevel, maxLevel`
- 그래픽: `characterName/Index`(필드 도트), `faceName/Index`(얼굴), `battlerName`(사이드뷰 전투 이미지)
- `equips`: 초기 장비 ID 배열(슬롯 순서)
- `traits`: 이 캐릭터 고유 특성

런타임 `Game_Actor`는 `actorId` 하나당 **인스턴스 하나**(`Game_Actors`가 ID로 캐시). → 같은 캐릭터를 두 장 보유한다는 개념이 없다(카드 게임에 중요, 6절).

### 1.2 Classes.json — 직업(성장 곡선 + 특성 묶음)
- `traits`
- `expParams`: [기본값, 추가값, 증가A, 증가B] 4개 → `Game_Actor.expForLevel`의 고정 공식에 투입
- `params`: **2차원 배열 `params[능력치ID][레벨]`** (8 × 레벨 수). 레벨별 기본 능력치 테이블 그대로 (`Game_Actor.paramBase`)
- `learnings`: `[{level, skillId, note}]` 레벨 도달 시 스킬 습득 (`Game_Actor.initSkills`, `levelUp`)

→ "공식이 아니라 **테이블**로 성장치를 들고 있다"는 점이 밸런싱 툴 관점에서 좋다(에디터가 곡선 생성기를 제공하고 결과는 표로 저장 — 추정: 에디터 기능).

### 1.3 Skills.json / Items.json — 사용 가능한 행동(UsableItem)
두 파일이 **공통 필드를 공유**한다:
- `scope`(대상 범위), `occasion`(사용 가능 상황), `speed`(행동 속도 보정), `successRate`(%), `repeats`(연속 횟수), `tpGain`(사용자 TP 획득), `hitType`(0 필중, 1 물리, 2 마법), `animationId`
- `damage`: `{type, elementId, formula, variance, critical}`
- `effects`: Effect 배열 (3절)
- `iconIndex, description, note`

스킬 전용: `stypeId`(스킬 타입), `mpCost`, `tpCost`, `message1/2`(사용 메시지), `requiredWtypeId1/2`(필요 무기 타입)
아이템 전용: `itypeId`(1 일반, 2 중요 등 — 추정), `price`, `consumable`

**scope 코드** (`Game_Action.isForOpponent`~`numTargets`):
| 값 | 의미 |
|---|---|
| 0 | 없음 |
| 1 / 2 | 적 1체 / 적 전체 |
| 3~6 | 적 무작위 1~4체 (`scope - 2`체) |
| 7 / 8 | 아군 1체 / 아군 전체 |
| 9 / 10 | 전투불능 아군 1체 / 전체 |
| 11 | 사용자 자신 |

**damage.type 코드** (`Game_Action.checkDamageType` 계열): 0 없음, 1 HP 데미지, 2 MP 데미지, 3 HP 회복, 4 MP 회복, 5 HP 흡수, 6 MP 흡수.
**damage.elementId**: -1이면 "일반 공격 속성"(사용자 무기·특성의 공격 속성 중 대상에게 가장 유리한 배율), 그 외는 System.elements 인덱스 (`Game_Action.calcElementRate`).
**occasion**: 0 항상, 1 전투 중, 2 메뉴, 3 사용 불가 (`Game_BattlerBase.isOccasionOk`).

### 1.4 Weapons.json / Armors.json — 장비(특성 운반체)
- `etypeId`(장비 슬롯 종류), `wtypeId` / `atypeId`(무기·방어구 타입)
- `params`: 길이 8 배열, 장착 시 능력치에 **덧셈** (`Game_Actor.paramPlus`)
- `traits`: 장착 중 부여되는 특성
- `price, iconIndex, description, note`, 무기는 `animationId`(일반 공격 애니메이션)

인벤토리는 `{id: 개수}` 맵 (`Game_Party._weapons`) → **개체별 강화 수치·내구도 같은 인스턴스 데이터가 없다.**

### 1.5 Enemies.json — 적
- `params`: 길이 8 (레벨 개념 없음, 고정값) (`Game_Enemy.paramBase`)
- `traits`, `exp`, `gold`
- `dropItems`: `[{kind(1 아이템/2 무기/3 방어구), dataId, denominator(1/N 확률)}]`
- `actions`: **행동 패턴 테이블** `[{skillId, conditionType, conditionParam1, conditionParam2, rating}]`
  - conditionType: 0 항상, 1 턴(a + b·n), 2 HP 비율 범위, 3 MP 비율 범위, 4 상태 걸림, 5 파티 최고 레벨 이상, 6 스위치 ON (`Game_Enemy.meetsCondition`)
  - rating(1~9): 조건을 만족한 행동 중 **최고 rating - 3 초과**인 것만 후보로 남기고, rating 가중 랜덤 (`Game_Enemy.selectAllActions`, `selectAction`)
- `battlerName, battlerHue`

→ 스크립트 없이 "조건 + 가중치" 테이블만으로 적 AI를 기획하는 방식. 단순하지만 기획자 친화적.

### 1.6 Troops.json — 적 편성 + 전투 이벤트
- `members`: `[{enemyId, x, y, hidden(도중 출현)}]`
- `pages`: 전투 이벤트 페이지 `[{conditions, span, list}]`
  - `conditions`: 턴 종료 / 턴 수(turnA + turnB·n) / 적 HP% / 액터 HP% / 스위치 — 각각 `...Valid` 플래그로 on/off
  - `span`: 0 전투당 1회, 1 턴당 1회, 2 조건 만족할 때마다 (`Game_Troop.setupBattleEvent`, `increaseTurn`)
  - `list`: 이벤트 명령 배열 (전투 중 대사·연출)

→ **보스전 중간 대사 연출**을 데이터로 넣는 구조. 스토리 연동 전투에 그대로 유용.

### 1.7 States.json — 상태이상/버프 상태
- `traits`: 걸려 있는 동안 적용되는 특성 (상태 = "일시적으로 붙는 특성 묶음")
- `restriction`: 0 없음, 1 적 공격, 2 아무나 공격, 3 아군 공격, 4 행동 불가 (`Game_BattlerBase.isConfused`, `canMove`)
- `priority`: 아이콘/메시지 정렬 우선순위 (`sortStates`)
- 지속: `autoRemovalTiming`(0 없음, 1 행동 종료 시, 2 턴 종료 시), `minTurns/maxTurns`(랜덤 지속)
- 해제 조건: `removeAtBattleEnd`, `removeByRestriction`, `removeByDamage + chanceByDamage(%)`, `removeByWalking + stepsToRemove`
- 연출: `iconIndex`, `motion`, `overlay`, `message1~4`(아군 걸림/적 걸림/지속/해제)
- 특수: **ID 1번 = 전투불능** 하드코딩 (`Game_BattlerBase.deathStateId`)

### 1.8 Animations.json — 전투 애니메이션
- `animation1Name/Hue`, `animation2Name/Hue`: 스프라이트 시트 2장 (192px 셀, 5열)
- `position`: 머리/중앙/발/화면
- `frames`: **3차원 배열** `frames[프레임][셀] = [패턴, x, y, 배율%, 회전°, 좌우반전, 불투명도, 블렌드]` (`Sprite_Animation.updateCellSprite`; 패턴 100 이상이면 2번 시트)
- `timings`: `[{frame, se, flashScope, flashColor[r,g,b,a], flashDuration}]` 특정 프레임에 효과음/화면 플래시

→ 타임라인을 "프레임 × 셀 배열"로 저장하는 저수준 포맷. 카드 게임 스킬 연출에는 파티클·트윈 기반이 더 적합(6절).

### 1.9 Tilesets.json / MapInfos.json / MapXXX.json — 맵 (제외 대상, 요약)
- Tileset: `mode`, `tilesetNames[9]`, `flags`(타일별 통행 비트)
- MapInfos: `[{name, parentId, order, expanded, scrollX, scrollY}]` 에디터 트리용 (scroll은 에디터 상태)
- Map: `width, height, data`(3차원 타일 ID), `tilesetId`, BGM/BGS 자동 재생, 전투배경, 원경(parallax), `encounterList`, `events`(위치 + 페이지별 조건·그래픽·이동·트리거·명령 리스트)
- **참고할 부분**: 이벤트 "페이지" 개념 — 조건(스위치/변수/셀프스위치/아이템/액터)을 만족하는 **가장 뒤 페이지**가 활성화. 스토리 진행에 따라 같은 대상의 반응이 바뀌는 구조로, VN 분기/허브 화면에 응용 가능.

### 1.10 CommonEvents.json — 공용 이벤트(재사용 스크립트)
- `{id, name, trigger(0 없음, 1 자동 실행, 2 병렬), switchId, list}`
- 아이템/스킬 효과(코드 44)나 다른 이벤트에서 호출 가능 → **"함수"** 역할

### 1.11 System.json — 전역 설정·용어·이름표
- 기본: `gameTitle, locale, currencyUnit, versionId, windowTone`
- 시작: `partyMembers`(시작 파티), `startMapId/X/Y`, 탈것 3종
- 이름 목록(인덱스 = ID): `elements, skillTypes, weaponTypes, armorTypes, equipTypes, switches, variables`
- 용어: `terms {basic, params, commands, messages}` — UI 문구 현지화 테이블 (`TextManager`가 사용)
- 오디오: `titleBgm, battleBgm, victoryMe, defeatMe, gameoverMe, sounds[]`(시스템 SE 순서 고정 배열)
- 옵션 플래그: `optSideView, optSlipDeath(슬립 데미지로 사망 허용), optDisplayTp, optExtraExp, ...`
- 기타: `magicSkills`(마법으로 간주할 스킬타입 — 마법반사 판정용), `attackMotions`, `menuCommands`, 전투 테스트 설정(`testBattlers, testTroopId`), 암호화(`encryptionKey` 등, json_docs 미기재)

AudioFile 공통 형태: `{name, volume, pitch, pan}`.

### 1.12 이벤트 명령 공통 형태
`{code, indent, parameters[]}` — 코드 101 대사, 102 선택지, 111 조건분기, 121 스위치, 122 변수, 231 그림 표시, 241 BGM, 301 전투, 355 스크립트, 356 플러그인 명령 등 (`Game_Interpreter.commandNNN`). 파라미터는 **위치 기반 배열**이라 의미는 각 명령 함수 안에만 있다.

## 2. Traits(특성) 시스템 — "패시브 수정자의 공통 언어"

### 2.1 형태
`{code, dataId, value}` 세 숫자. `code` = 무엇을 바꾸나, `dataId` = 어느 대상(능력치 ID·속성 ID·상태 ID…), `value` = 얼마나.

### 2.2 출처 (traitObjects)
| 전투원 | 특성을 모으는 객체들 | 위치 |
|---|---|---|
| 기본 | 현재 걸린 **States** | `Game_BattlerBase.traitObjects` |
| 아군 | States + **Actor** + **Class** + 장착 중인 **Weapons/Armors** | `Game_Actor.traitObjects` |
| 적 | States + **Enemy** | `Game_Enemy.traitObjects` |

캐릭터·직업·장비·상태·적이 **모두 같은 `traits` 배열 형식**을 가진다. 그래서 "독 저항"은 캐릭터 고유 능력이든, 액세서리든, 일시 버프 상태든 같은 데이터로 표현된다.

### 2.3 조회·합산 방식 (`rpg_objects/Game_BattlerBase.js`)
1. `allTraits()`: 위 객체들의 `traits`를 전부 이어 붙인 평면 배열
2. `traits(code)` / `traitsWithId(code, id)`: 코드(와 ID)로 필터
3. 합산 연산 4종:
   - `traitsPi` — **곱** (초기값 1): 배율류
   - `traitsSum` — 같은 dataId의 **합** (초기값 0): 확률 가산류
   - `traitsSumAll` — dataId 무시하고 전부 합
   - `traitsSet` — dataId들의 **집합**: on/off, 허용 목록류

즉 "특성 코드마다 어느 합산 연산을 쓰느냐"만 정하면 새 규칙이 생긴다. 캐시 없이 조회할 때마다 다시 계산한다.

| 63 | COLLAPSE_TYPE 소멸 연출 | 0 일반 1 보스 2 즉시 3 소멸 안 함 | - | 최댓값 | 적 사망 연출 `Game_Enemy.performCollapse` (0·1은 코드 확인, 2·3 의미는 추정) |
| 64 | PARTY_ABILITY | 0 조우 반감 1 조우 무효 2 기습 방지 3 선제 증가 4 골드 2배 5 드롭 2배 | - | 전투 멤버 중 한 명이라도 | `Game_Party.partyAbility` |

### 2.5 최종 능력치 공식 (`Game_BattlerBase.param`)
`(기본값 + 덧셈 보정) × 특성 배율(곱) × 버프 배율` → 최소/최대값으로 자르고 반올림.
- 기본값: 액터는 `Class.params[id][레벨]`, 적은 `Enemy.params[id]`
- 덧셈 보정: 영구 성장(`_paramPlus`, 아이템 효과 42) + 장비 `params`
- 버프 배율: 버프 단계(-2~+2) × 25% (`paramBuffRate`)
- 상한: HP 999999, MP 9999, 나머지 999 (`paramMax` — 플러그인이 흔히 덮어쓰는 지점)

### 2.6 왜 범용적인가
1. **단일 형식**: 모든 패시브 효과가 `(code, dataId, value)` 하나로 표현 → 에디터는 "특성 추가" UI 하나만 만들면 캐릭터·직업·장비·상태·적 탭에서 공용.
2. **출처 무관성**: 런타임은 특성이 어디서 왔는지 신경 쓰지 않는다. 새 출처(예: 파티 오라, 지형)를 추가하려면 `traitObjects`에 객체 하나만 더 넣으면 된다.
3. **조합이 자동**: 곱/합/집합 규칙이 정해져 있어 여러 출처의 효과가 자동으로 쌓인다.
4. **질의 API**: 게임 로직은 "속성 3 배율은?"처럼 묻기만 한다(`elementRate(3)`).
5. **확장 비용 낮음**: 새 코드 하나 + 조회 함수 하나.

### 2.7 한계
- 코드·dataId·value 의미가 **숫자 + 코드 안 switch**에만 있다. 데이터만 보고는 의미를 모른다.
- 합산 규칙이 코드별로 고정(예: 물리피해율은 무조건 곱 → 50% 경감 두 개 = 25%, 기획 의도와 다를 수 있다).
- **조건부 특성 불가**: "HP 50% 이하일 때 공격력 +30%", "물 속성 아군이 2명 이상이면" 같은 조건을 표현할 수 없다 → 플러그인 + note 태그로 해결하는 게 MV 생태계의 관행.
- **트리거형 효과 불가**: "피격 시", "턴 시작 시", "아군 사망 시" 같은 이벤트 반응형 능력은 특성 체계 밖이다. (반격 `cnt`, 재생 `hrg`처럼 소수만 특수 처리)
- 매 조회마다 전체 재계산(성능).

## 3. Effects(효과) 시스템 — "사용 시 즉발 효과의 공통 언어"

### 3.1 형태
`{code, dataId, value1, value2}`. Skills/Items의 `effects` 배열에만 존재. Traits가 "지속 수정자"라면 Effects는 "한 번 일어나는 사건".

### 3.2 실행 흐름 (`Game_Action.apply`)
1. `testApply`: 이 대상에게 쓸 의미가 있나 (전투 중이 아니면 HP 가득 찬 대상에게 회복 금지 등, `testItemEffect`)
2. 명중 판정: `successRate × 사용자 hit`(물리) — 실패하면 miss
3. 회피 판정: 물리면 대상 `eva`, 마법이면 `mev`
4. 명중 시: `damage.type > 0`이면 치명타 판정 → 데미지 계산·적용 (4절)
5. **effects 배열을 순서대로** `applyItemEffect`로 적용 (코드별 switch)
6. 사용자 TP 획득(`tpGain × tcr`)
7. 행동 시작 시 별도로 `applyGlobal`이 공통 이벤트(코드 44)를 예약

### 3.4 평가
- 장점: 스킬 = "데미지 1개 + 효과 리스트"로 대부분의 RPG 스킬을 데이터만으로 조립. 에디터 UI도 "효과 추가" 하나로 통일.
- 한계: 효과에 **자기 대상 범위가 없다**(스킬의 scope 하나를 모든 효과가 공유 → "적에게 데미지 + 자신 버프"를 표현 못 함). 조건부 효과("대상이 독 상태면 추가 피해") 불가. 효과 간 순서·연쇄 개념 없음. 코드 44로 공용 이벤트를 부르는 우회로는 대상 정보가 넘어가지 않는다.

## 4. 데미지 공식 — 문자열 eval

### 4.1 구조 (`Game_Action.evalDamageFormula`, `makeDamageValue`)
- `damage.formula`는 JS 식 문자열. 예: `a.atk * 4 - b.def * 2`
- 평가 환경: `a` = 사용자(Game_Battler), `b` = 대상, `v` = 게임 변수 배열(`$gameVariables._data`). 이 세 지역 변수 범위에서 `eval`.
- 결과는 `max(값, 0)` 후 회복 타입(3, 4)이면 음수로 뒤집음. NaN 또는 예외면 **조용히 0**.
- 이후 고정 파이프라인: × 속성 배율(`calcElementRate`) → × 물리/마법 피해율(`pdr/mdr`) → (회복이면) × 회복효과율(`rec`) → 치명타 ×3(`applyCritical`) → 분산 ±variance%(`applyVariance`, 두 난수 합으로 중앙 집중) → 방어 시 ÷(2 × grd)(`applyGuard`) → 반올림.

### 4.2 장점
- 기획자가 스킬마다 공식을 자유롭게 쓴다. `b.hp`, `a.level`, `b.isStateAffected(4) ? 2 : 1` 같은 조건식도 가능 → 엔진 수정 없이 특수 스킬 제작.
- 파이프라인 후반(속성·치명·분산·방어)은 엔진이 공통 처리 → 공식은 "기본 위력"만 신경 쓰면 됨.

### 4.3 단점
- **보안**: 임의 코드 실행. 사용자 생성 콘텐츠·서버 검증에 부적합.
- **부작용**: 공식 안에서 `b.addState(...)` 같은 호출이 가능하고, 자동전투/혼란 AI 평가(`Game_Action.evaluateWithTarget`)도 같은 `makeDamageValue`를 호출하므로 **평가만 해도 부작용이 발생**할 수 있다.
- **오류 은폐**: 오타가 나도 0 데미지로 넘어감 → 버그 발견이 늦다.
- **정적 분석 불가**: 툴이 "이 스킬의 기대 데미지 그래프"를 그리거나 밸런스 시뮬레이션에서 의존 스탯을 추출할 수 없다. 이름 변경 리팩터링 불가.
- 성능: 매 적용마다 문자열 파싱 (추정: JS 엔진 캐시가 일부 완화).
- 모바일 빌드·CSP 환경에서 `eval` 금지 정책과 충돌 가능.

## 5. note 태그(메타데이터)

- 모든 레코드의 `note` 텍스트에서 정규식 `<이름>` 또는 `<이름:값>`을 찾아 `record.meta[이름] = true | "값"`으로 저장 (`DataManager.extractMetadata`). 맵 자체와 맵 이벤트에도 적용.
- 엔진 코어는 `meta`를 **전혀 읽지 않는다**. 순수하게 플러그인용 확장 슬롯이다.
- 장점: DB 스키마를 바꾸지 않고 아무 데이터에나 사용자 필드를 붙일 수 있다(예: `<등급:SSR>`, `<계약조건:...>`). 에디터 수정 없이 확장.
- 단점: 값이 전부 문자열(타입 없음, 플러그인이 각자 파싱), 오타 검출 불가, 같은 태그 이름을 두 플러그인이 다르게 쓰면 충돌, 에디터에서 자동완성·검증 불가, 같은 태그 반복 시 마지막 값만 남음, 값에 `>` 문자 불가.
- MV 생태계에서 note 태그는 사실상 **"에디터가 지원하지 않는 필드를 넣는 비상구"** — 이것이 많이 쓰일수록 공식 스키마가 부족하다는 신호다.

## 6. 카드 수집형 RPG 적용 제안

전제(ENGINE_TOOL_PLAN.md 기준): TypeScript 런타임, 전투 로직은 화면과 분리된 순수 로직, 에디터가 JSON을 내보냄, 1인 개발.

### 6.1 그대로 쓸 것 (개념 차용)

| MV 개념 | 카드 RPG에서의 쓰임 |
|---|---|
| **Traits `(code, dataId, value)` + 출처 수집 + 합산 규칙** | 카드 고유 패시브, 장비/성유물, 계약 보너스, 전투 중 상태를 **하나의 수정자 형식**으로 통일. `traitObjects`에 해당하는 "수정자 출처 목록" 함수만 카드·장비·버프·파티 오라로 확장 |
| **Effects 리스트** | 스킬 = 효과 블록의 순서 있는 리스트. 에디터에서 블록 추가 UI |
| **능력치 파이프라인** (기본 + 덧셈) × 배율 × 버프 → clamp | 그대로. 단 단계(기본/평면/퍼센트/최종)를 명시적으로 이름 붙이기 |
| **성장치 테이블** (Class.params[능력치][레벨]) | 카드 등급·레벨별 능력치 테이블. 에디터에 곡선 생성기 + 표 저장 |
| **적 행동 패턴 테이블** (조건 + rating) | 몬스터 AI 기본형. 조건 종류만 카드 게임용으로 교체 |
| **Troop 전투 이벤트 페이지** (조건 + span + 명령 리스트) | 보스전 중 대사·CG·BGM 전환 — 스토리 연동 전투의 핵심 |
| **세이브엔 ID만** (`Game_Item` 패턴) | 보유 카드 = `{instanceId, cardId, level, ...}`, 정의 데이터는 DB에서 조회 |
| System의 **이름 목록 테이블**(elements, skillTypes …) | 속성·등급·진영 목록을 별도 테이블로, 다른 데이터는 참조만 |
| 상태의 지속·해제 옵션 (턴 범위, 피격 해제 확률, 전투 종료 해제, 우선순위) | 거의 그대로 |
| 이벤트 명령 리스트 + 인터프리터 | VN 에피소드 스크립트 (01 문서 3.5) |

### 6.2 바꿀 것

| MV | 문제 | 제안 |
|---|---|---|
| 숫자 코드 (`code: 22, dataId: 2`) | 읽기 어려움, 의미가 코드에만 | 문자열 판별자: `{ kind: 'stat', stat: 'critRate', op: 'add', value: 0.1 }`. TypeScript 판별 유니언 타입 → 에디터 폼 자동 생성 + 컴파일 타임 검증 |
| 배열 인덱스 = ID | 삭제·병합 충돌 | 안정 문자열 ID (`card.ariel`, `skill.flame_burst`) + 표시 순서 필드 |
| `Game_Actor`가 액터ID당 1개 | **같은 카드 중복 보유·돌파(한계 돌파) 불가** | 정의(`CardDef`)와 보유 인스턴스(`OwnedCard {uid, defId, level, exp, ascension, bond, equips}`) 분리 |
| 무기·방어구 = 개수 카운트 | 개체별 강화 불가 | 장비도 인스턴스화 (필요 시) |
| Actor + Class 2단 | 카드 게임엔 직업 개념이 약함 | `CardDef` 하나에 등급·속성·역할·성장 테이블·스킬 슬롯을 직접 두고, 공통 성장 곡선은 `GrowthCurve` 테이블로 참조 |
| 특성 = 무조건 상시 | 조건부 패시브 표현 불가 | 수정자에 `condition?` 필드 추가 (`{ when: 'hpBelow', ratio: 0.5 }`, `{ when: 'allyCount', element: 'water', min: 2 }`). 조건 종류는 열거형으로 제한 |
| 트리거형 능력 없음 | "피격 시/턴 시작 시/처치 시" 카드 능력이 핵심 | **Trigger 시스템 추가**: `{ on: 'turnStart'|'onHit'|'onKill'|..., condition?, effects: [...] }`. 전투 로직이 이벤트를 발행하면 각 전투원의 트리거를 조회 |
| Effect가 스킬 scope 공유 | "적 데미지 + 자기 버프" 불가 | 효과 블록마다 `target` 필드 (`'skillTarget' | 'self' | 'allAllies' | ...`) |
| 데미지 = 문자열 eval | 보안·분석·부작용 | **구조화 공식**: `{ base: [{ stat: 'atk', from: 'user', coef: 2.4 }, { stat: 'def', from: 'target', coef: -1.0 }], flat: 0 }` 같은 선형 계수 조합 + 소수의 이름 붙은 특수 공식(코드 등록). 에디터가 스탯별 기대 데미지 그래프를 바로 그릴 수 있음. 정말 자유 공식이 필요하면 eval 대신 안전한 작은 수식 파서(사칙연산 + 화이트리스트 변수) |
| 합산 규칙 코드 고정 | 곱연산 중첩이 기획과 어긋남 | 수정자 `op`(add/mul/override)와 **스택 그룹**(같은 그룹은 합산 후 곱 등)을 데이터로 지정 |
| note 태그 | 타입 없는 문자열 | 정식 스키마 필드로 승격. 진짜 임시 확장은 `extra: Record<string, unknown>`에 두되 에디터가 경고 |
| 세이브 = 클래스명 직렬화 | 리팩터링 시 깨짐 | 순수 JSON + `saveVersion` + 마이그레이션 |
| 행동 순서 = 민첩 + 난수 | 카드 게임은 결정론·예측 가능성이 중요 | 순서 규칙을 데이터/설정으로 (고정 속도 순, 행동 게이지 등), 난수는 **시드 RNG**로 → 리플레이·서버 검증·시뮬레이션 재현 |
| 연출과 로직이 같은 틱에서 대기 | 시뮬레이터 불가 | 로직 → 이벤트 로그 → 연출 재생 (01 문서 9절) |

### 6.3 버릴 것

- **맵·타일·필드 이동 관련 전부**: Tilesets, Map data, MapInfos, 이벤트 이동 경로, 탈것, 걷기 해제 상태(`removeByWalking`), 조우(encounter) 설정, 바닥 피해율(sparam 8), 파티 능력 0~3(조우·기습).
- **장비 타입 체계 일부**: 무기 타입별 장비 가능(51/52), 장비 고정·봉인(53/54), 이도류(55), 스킬의 필요 무기 타입 — 카드 게임에 장비가 있더라도 훨씬 단순할 가능성이 높음 (기획 확정 전까지 보류).
- **Animations.json의 프레임×셀 배열 포맷**: 카드 스킬 연출은 트윈·파티클·Spine류 타임라인이 적합. "특정 시점에 SE/플래시" 타이밍 개념만 남김.
- **문자열 eval** (데미지 공식, 스크립트 명령 355, 조건분기 스크립트).
- **프로토타입 덮어쓰기 플러그인 + note 태그 의존 확장 방식**.
- **ID 1 = 전투불능 같은 하드코딩 규약** → 상태에 `isDeath: true` 같은 명시 플래그로.
- MP/TP 이원 자원: 카드 게임 자원 체계(코스트·에너지·게이지)에 맞게 재설계 — 개념만 참고.

### 6.4 카드 데이터 스키마 스케치 (설계 출발점, 예시)

```ts
// 정의 데이터 (에디터가 편집, 런타임은 읽기 전용)
CardDef {
  id: 'card.ariel'            // 안정 ID
  name, rarity: 'R'|'SR'|'SSR', element: ElementId, role: RoleId
  growth: GrowthCurveId | StatTable   // Class.params 대응
  baseSkills: SkillId[]; ultimate?: SkillId
  passives: Modifier[]        // Traits 대응 (+ condition)
  triggers: Trigger[]         // MV에 없음, 신규
  contract: ContractCondition[]  // 획득·계약 조건 (스토리 플래그, 재료, 호감도 등)
  story: { unlockEpisode?: EpisodeId, voice?, cg? }
}
Modifier { kind, target(stat/element/state...), op: 'add'|'mul'|'set', value, condition?, stackGroup? }
SkillDef { id, cost, targetRule, damage?: DamageSpec, effects: EffectBlock[] }  // Effects 대응
EffectBlock { kind, target: 'skillTarget'|'self'|..., chance?, condition?, ... }

// 보유 데이터 (세이브)
OwnedCard { uid, defId, level, exp, ascension, bond, equipped: [...] }
```

계약 조건(`contract`)은 MV에 대응물이 없다. 가장 가까운 것은 이벤트 페이지 조건(스위치·변수·아이템·액터 보유)이므로, **조건 블록 형식(종류 + 파라미터)을 이벤트 조건·전투 이벤트 조건·패시브 조건·계약 조건이 공유**하도록 하나의 `Condition` 타입으로 통일하는 것을 권장한다. MV는 이 조건 구조가 파일마다 제각각(EventPage::Conditions, BattleEventPage::Conditions, Enemy::Action의 conditionType)이어서 재사용이 안 되는 점이 약점이다.
