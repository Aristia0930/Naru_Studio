> 출처: RPG Maker MV corescript (MIT, KADOKAWA/YOJI OJIMA), 분석일 2026-10-26
> 분석 대상 버전: `rpg_core.js v1.6.1 (community-1.3b)` (js/rpg_core/_header.js 기준)
> 범위: 이벤트 명령 데이터 구조, 인터프리터 실행 모델, 명령 코드 전체 분류, 스위치/변수/페이지 조건, 메시지 시스템, 그리고 "비주얼노벨식 에피소드 연출 에디터"로의 적용 판단.

## 0. 한 줄 요약

MV의 이벤트는 **"들여쓰기(indent) 값이 붙은 명령의 평평한 배열"** 이고, 이를 **프레임 단위로 한 줄씩 진행하는 협력형(cooperative) 인터프리터**가 실행한다. 분기/루프는 트리가 아니라 indent 비교로 "건너뛰기"를 해서 구현한다. 구조는 단순하고 저장·재개가 쉽지만, 명령 파라미터가 위치 기반 배열이라 사람이 읽기 어렵고 전역 상태(`$gameXxx`)에 강하게 묶여 있다.

## 1. 이벤트 명령 리스트의 데이터 구조

### 1.1 EventCommand = `{ code, indent, parameters }`
- `json_docs.js`의 `~ EventCommand` 정의: `code`(명령 번호), `indent`(들여쓰기 깊이), `parameters`(명령별 위치 기반 배열) 세 필드뿐이다.
- 하나의 "이벤트 페이지" / "공통 이벤트" / "전투 이벤트 페이지"는 모두 이 명령들의 **1차원 배열(`list`)** 을 가진다.
- 블록 구조(조건 분기 안의 명령들 등)는 **중첩 객체가 아니라 indent 숫자**로 표현된다. 예: 조건 분기(111)는 indent N, 그 안의 명령은 N+1, `Else`(411)와 `분기 끝`(412)은 다시 N.
- 리스트 끝에는 code 0, indent 0인 "빈 명령"이 항상 붙는다(에디터가 넣는 종단 마커). 블록 끝마다도 code 0 명령이 들어간다 **(추정: 에디터 출력 관례. 런타임은 code 0에 핸들러가 없으므로 그냥 지나간다)**.

### 1.2 "연속 행(continuation)" 코드
여러 줄 데이터를 가진 명령은 **본 명령 + 후속 행 명령** 으로 나뉜다. 후속 행은 독립 실행되지 않고 본 명령이 `nextEventCode()`로 미리 읽어 소비한다.

| 본 명령 | 후속 행 | 용도 |
|---|---|---|
| 101 텍스트 표시 | 401 | 대사 한 줄씩 |
| 105 스크롤 텍스트 | 405 | 스크롤 텍스트 한 줄씩 |
| 108 주석 | 408 | 주석 추가 줄 (플러그인들이 메타데이터로 활용) |
| 355 스크립트 | 655 | JS 코드 추가 줄 |
| 205 이동 루트 설정 | 505 | 에디터 표시용 루트 명령 (런타임은 params[1]의 route 객체를 사용) |
| 302 상점 | 605 | 상품 목록 추가 |

### 1.3 "구조 마커" 코드 (핸들러 없음)
`Game_Interpreter.prototype.executeCommand`는 `'command' + code` 이름의 메서드가 **없으면 아무것도 안 하고 다음 줄로 넘어간다**. 그래서 다음 코드들은 실행 의미 없이 블록 경계 표시용으로만 존재한다.
- 404(선택지 끝), 412(분기 끝), 604(전투 결과 분기 끝), 0(블록/리스트 끝), 401/405/408/505/605/655(이미 본 명령이 소비)
- 이 설계 덕분에 **"모르는 명령은 무시"** 가 기본 동작이 되고, 플러그인이 `commandXXX`를 추가하는 것만으로 명령 세트가 확장된다.

## 2. 인터프리터 실행 모델 (`rpg_objects/Game_Interpreter.js`)

### 2.1 핵심 상태 필드
| 필드 | 의미 |
|---|---|
| `_list`, `_index` | 실행 중인 명령 배열과 프로그램 카운터 |
| `_indent`, `_params` | 현재 명령의 indent / parameters (실행 직전에 세팅) |
| `_branch` | **indent → 분기 결과** 맵. 조건 분기의 true/false, 선택지 번호, 전투 결과(0승/1도주/2패)를 저장 |
| `_waitCount` | 남은 대기 프레임 수 |
| `_waitMode` | 문자열 대기 모드(`'message'`, `'video'`, `'action'` 등) |
| `_childInterpreter` | 공통 이벤트 호출 시 생성되는 자식 인터프리터 |
| `_depth` | 자식 중첩 깊이 (100 이상이면 예외: `checkOverflow`) |
| `_mapId`, `_eventId` | 실행 문맥(어느 맵의 어느 이벤트인지; 셀프 스위치 키에 사용) |
| `_eventInfo` | 에러 리포트용 출처 정보 |

### 2.2 한 프레임의 실행 루프 (`update`)
매 프레임 `update()`가 호출되면 다음을 **반복**한다.
1. 자식 인터프리터가 있으면 그것부터 갱신(`updateChild`). 자식이 아직 실행 중이면 이번 프레임 종료.
2. 대기 중이면 종료(`updateWait` = `updateWaitCount` → `updateWaitMode`).
3. 씬 전환 중이면 종료.
4. 현재 명령 실행(`executeCommand`). 명령 함수가 **false를 반환하면 이번 프레임 종료**(= yield).
5. 한 프레임에 10만 개 이상 명령을 돌리면 강제 종료(`checkFreeze`, 무한루프 보호).

즉 **명령 함수의 반환값이 곧 "계속/양보" 신호**다.
- `true` 반환: 즉시 다음 명령으로 넘어감(같은 프레임에서 계속 실행).
- `false` 반환: 이번 프레임은 여기서 멈춤. 이때 `_index`를 증가시키지 않으므로 다음 프레임에 **같은 명령을 다시 시도**한다(예: 메시지 창이 아직 바쁘면 101은 아무것도 안 하고 false → 다음 프레임 재시도).
- 메시지(101), 페이드(221/222)처럼 "한 번 실행 후 기다려야 하는" 명령은 스스로 `_index++` 하고 false를 반환하는 패턴을 쓴다.

### 2.3 대기(wait)의 두 종류
1. **카운트 대기**: `wait(n)` → n프레임 동안 정지. 명령 230(대기), 페이드(221/222는 고정 24프레임 `fadeSpeed`), 그리고 "완료까지 대기" 체크박스가 있는 연출 명령들(223 색조, 224 플래시, 225 흔들기, 232 그림 이동, 234 그림 색조, 236 날씨)이 사용.
2. **모드 대기**: `setWaitMode(mode)` → 매 프레임 외부 객체에 "아직 바쁜가?"를 물어봄(`updateWaitMode`). 조건이 풀리면 모드가 자동 해제.
   - `message`: `$gameMessage.isBusy()` (텍스트/선택지/숫자입력/아이템선택이 남아있는 동안)
   - `transfer`, `scroll`, `route`, `animation`, `balloon`, `gather`: 맵/캐릭터 관련
   - `action`: 전투 강제 행동 완료(`BattleManager.isActionForced`)
   - `video`: 동영상 재생 중
   - `image`: 이미지 로딩 대기 — 이 버전 소스에서는 **이 모드를 설정하는 명령이 없다**(분기만 존재).
- 설계 요점: 인터프리터는 연출 객체를 직접 기다리지 않고 **폴링**한다. 연출 객체(`Game_Screen`, `Game_Message` 등)는 자기 상태만 가지며 인터프리터를 모른다. → 결합도가 낮다.

### 2.4 분기 (indent + skipBranch)
- 공통 도구 `skipBranch()`: 현재 indent보다 **깊은** 다음 명령들을 전부 건너뛴다. 즉 "이 블록의 본문을 실행하지 않음".
- 조건 분기 111: 조건을 평가해 `_branch[indent] = 결과`, false면 본문 skip. Else 411은 `_branch[indent]`가 false가 아니면 자기 본문 skip.
- 선택지 102: 메시지 콜백으로 선택 번호를 `_branch[indent]`에 기록. 각 `When [n]`(402)은 저장된 번호와 자기 번호가 다르면 skip, `When Cancel`(403)은 값이 0 이상(=일반 선택)이면 skip.
- 전투 처리 301: `BattleManager.setEventCallback`으로 결과(0/1/2)를 `_branch[indent]`에 기록 → 601/602/603이 동일 방식으로 분기.
- **패턴 정리: "분기를 만드는 명령은 결과를 `_branch[자기 indent]`에 쓰고, 같은 indent의 케이스 명령들은 그 값을 읽어 자기 본문을 건너뛸지 결정한다."** 트리 없이 평평한 배열로 if/switch를 표현하는 핵심 아이디어.

### 2.5 루프와 점프
- 루프 112: 아무 일도 하지 않는 시작 마커. `Repeat Above`(413): 같은 indent의 명령(=112)을 찾을 때까지 `_index`를 거꾸로 되감는다.
- 루프 탈출 113: 앞으로 스캔하며 중첩된 112/413 짝을 세고, 자기 루프의 413을 만나면 그 위치로 이동(다음 줄부터 실행).
- 레이블 118 / 레이블 점프 119: 리스트 전체에서 같은 이름의 118을 선형 검색 후 `jumpTo`. 점프 구간에서 지나친 indent들의 `_branch` 값을 지워서 오래된 분기 결과가 남지 않게 한다.
- 이벤트 처리 중단 115: `_index`를 리스트 끝으로 보냄 → 다음 루프에서 `terminate`.
- 참고: 119는 성공 시 반환값이 undefined(=false 취급)라서 **점프 직후 한 프레임 양보** 한다(Game_Interpreter.js:command119). 루프 남용 시 프레임 소모의 원인이 될 수 있음.

### 2.6 공통 이벤트와 자식 인터프리터
- 명령 117(공통 이벤트): `$dataCommonEvents[id].list`로 **새 Game_Interpreter(depth+1)** 를 만들어 `_childInterpreter`에 둔다(`setupChild`). 부모는 자식이 끝날 때까지 매 프레임 자식만 돌린다 → **동기 서브루틴 호출**.
- 자식은 부모의 `_eventId`를 물려받으므로(같은 맵일 때) 공통 이벤트 안에서의 셀프 스위치 조작이 호출한 이벤트 기준으로 동작한다.
- 공통 이벤트의 `trigger`: 0=없음(호출 전용), 1=자동 실행(스위치 ON 동안 메인 인터프리터를 점유), 2=병렬(스위치 ON 동안 독립 인터프리터로 반복 실행).
  - 병렬: `Game_CommonEvent`가 스위치 조건을 만족하면 자기 전용 인터프리터를 갖고, 끝나면 처음부터 다시 setup하여 **무한 반복**(`Game_CommonEvent.prototype.update`).
- **예약(reserve) 공통 이벤트**: 아이템/스킬 효과 44(공통 이벤트) 등은 즉시 실행하지 않고 `$gameTemp.reserveCommonEvent(id)`로 예약 → 메인 인터프리터가 비었을 때 `setupReservedCommonEvent`로 가져간다. 전투 중엔 `Game_Troop.setupBattleEvent`가 가져간다.

### 2.7 여러 인터프리터의 공존 (병렬 실행)
| 인터프리터 | 소유자 | 성격 |
|---|---|---|
| 메인 | `Game_Map._interpreter` | **동시에 하나만**. 플레이어 조작/자동 실행 이벤트가 사용. 실행 중이면 플레이어 이동 불가(`Game_Map.isEventRunning`) |
| 병렬 이벤트 | 각 `Game_Event._interpreter` (trigger 4) | 페이지 조건 만족 동안 반복 |
| 병렬 공통 이벤트 | 각 `Game_CommonEvent._interpreter` | 스위치 ON 동안 반복 |
| 전투 이벤트 | `Game_Troop._interpreter` | 전투 중 메인 역할 |
| 자식 | 각 인터프리터의 `_childInterpreter` | 공통 이벤트 호출 |

- 메인 인터프리터 선택 우선순위(`Game_Map.setupStartingEvent`): 예약 공통 이벤트 → 테스트 이벤트 → 시작 플래그가 선 맵 이벤트 → 자동 실행 공통 이벤트.
- 진짜 스레드가 아니라 **모두 같은 프레임 루프 안에서 차례로 update되는 코루틴**이다. 따라서 경쟁 조건은 "같은 프레임에서 먼저 도는 쪽이 이긴다" 수준이고, `$gameMessage`처럼 **하나뿐인 전역 자원**을 두 인터프리터가 동시에 쓰면 충돌한다(병렬 이벤트에서 메시지를 띄우면 메인과 겹치는 고전적 문제의 원인).

### 2.8 그 밖의 실행 모델 특징
- **이미지 선로딩**: `setup` 시 `Game_Interpreter.requestImages(list)`가 리스트 전체를 스캔해 얼굴(101), 그림(231), 애니메이션(212/337) 등의 이미지를 미리 요청한다. 공통 이벤트(117)는 재귀적으로 따라가되 중복 방지 목록을 쓴다. → **명령 리스트가 정적 데이터라서 실행 전 리소스 의존성 분석이 가능**하다는 장점을 실제로 활용한 사례.
- **에러 문맥**: 명령 실행 중 예외에 `_eventInfo`(이벤트 종류/ID/페이지)와 줄 번호를 붙여 다시 던진다(`executeCommand`). 툴의 디버그 표시에 그대로 쓸 만한 아이디어.
- **저장/재개**: 세이브에는 `$gameMap`이 들어가고 그 안에 메인 인터프리터가 있으므로 인터프리터 상태(리스트·인덱스·분기)가 직렬화된다(`DataManager.makeSaveContents`). 반면 `$gameMessage`, `$gameTemp`, `$gameTroop`은 저장되지 않는다(주석으로 명시). 메뉴 저장은 이벤트 실행 중엔 막혀 있어 실무상 문제는 적다.
- **탈출구**: 스크립트 355(임의 JS `eval`), 조건 분기의 스크립트 조건, 변수 조작의 스크립트 피연산자, 플러그인 명령 356(문자열을 공백으로 split해서 `pluginCommand`로 넘김; 기본 구현은 빈 함수). → 확장성은 크지만 정적 분석·검증·보안은 포기한 설계.

## 3. 전체 명령 코드 표

`Game_Interpreter.js`에 구현된 `commandNNN` 기준. "대기" 열: ●=항상 대기/양보, ○=옵션으로 완료 대기, 빈칸=즉시.

### 3.1 메시지
| 코드 | 이름 | 대기 | 비고 |
|---|---|---|---|
| 101 (+401) | 텍스트 표시 | ● message | 얼굴 이미지/인덱스, 배경(창/어둡게/투명), 위치(상/중/하). 바로 뒤가 102/103/104면 **같은 창에 묶어서** 함께 띄움 |
| 102 | 선택지 표시 | ● message | 선택지 배열, 취소 동작, 기본 선택, 위치, 배경 |
| 402 / 403 / 404 | When [n] / When Cancel / 선택지 끝 | | `_branch` 기반 |
| 103 | 숫자 입력 | ● message | 결과를 변수에 저장 |
| 104 | 아이템 선택 | ● message | 결과(아이템 ID)를 변수에 저장 |
| 105 (+405) | 스크롤 텍스트 | ● message | 속도, 빨리감기 금지 |

### 3.2 흐름 제어

## 4. 스위치 · 변수 · 셀프 스위치 · 페이지 조건

### 4.1 저장소
| 클래스 | 키 | 값 | 특징 |
|---|---|---|---|
| `Game_Switches` | 정수 ID(1부터) | boolean | 범위 밖 ID 무시(`$dataSystem.switches.length` 기준). 변경 시 `$gameMap.requestRefresh()` |
| `Game_Variables` | 정수 ID | 숫자(사실상 아무 JS 값 가능) | 변경 시 refresh 요청 |
| `Game_SelfSwitches` | `[맵ID, 이벤트ID, 'A'~'D']` 배열(객체 키로 문자열화됨) | true만 저장, false면 키 삭제 | 이벤트 하나에 딸린 지역 플래그 4개 |

- 이름은 데이터베이스(`$dataSystem.switches/variables`)에 **ID별 표시 이름**으로만 존재하고, 런타임은 오직 숫자 ID로 접근한다. → 에디터 편의성은 이름에, 런타임 안정성은 ID에 의존.
- 값이 바뀔 때마다 **"맵 refresh 요청" 이벤트를 발생**시키는 단순한 관찰자 패턴. refresh 때 모든 이벤트의 페이지를 재평가하고 병렬 공통 이벤트를 켜고 끈다(`Game_Map.refresh`).

### 4.2 이벤트 페이지 조건 (`Game_Event.meetsConditions`, `findProperPageIndex`)
- 맵 이벤트는 여러 "페이지"를 갖고, 각 페이지는 조건 + 외형 + 트리거 + 명령 리스트를 가진다.
- 페이지 조건은 **고정된 AND 슬롯들**: 스위치1, 스위치2, 변수(≥ 값만 가능), 셀프 스위치, 아이템 보유, 액터 파티 소속. 각 슬롯은 `xxxValid` 플래그로 켜고 끈다.
- **마지막 페이지부터 거꾸로 검사해 처음 만족하는 페이지가 활성** → "번호가 큰 페이지가 우선순위가 높다." 진행도에 따라 페이지를 추가하는 방식으로 상태 머신을 표현하는 관례.
- 트리거: 0 결정 키, 1 플레이어 접촉, 2 이벤트 접촉, 3 자동 실행, 4 병렬.
- 한계: OR, 범위 비교, 변수끼리 비교, "≤" 등은 페이지 조건으로 불가 → 결국 페이지 안에서 조건 분기(111)로 처리하거나 플러그인에 의존.

### 4.3 전투 이벤트 페이지 조건 (`Game_Troop.meetsConditions`)
- 턴 종료 시, 턴 수(A + B×n), 적 n번 HP ≤ %, 액터 HP ≤ %, 스위치. 이것도 AND 슬롯.
- **조건을 하나도 안 켠 페이지는 실행되지 않는다**(코드에 명시).
- `span`(실행 범위): 0=전투당 1회, 1=턴당 1회, 2=조건 만족 동안 매번. 실행 여부는 `_eventFlags[page]`로 기록, 턴 증가 시 span 1 페이지만 리셋(`increaseTurn`). 자세한 내용은 04 문서.

### 4.4 변수 조작의 "게임 데이터" 피연산자
`gameDataOperand`가 아이템 개수, 액터 레벨/경험치/HP/MP/능력치, 적 HP/MP/능력치, 캐릭터 좌표·방향, 파티 n번 액터 ID, 맵 ID, 파티 인원, 골드, 걸음 수, 플레이 시간, 타이머, 세이브/전투/승리/도주 횟수를 읽어온다. → **"게임 상태 → 변수"로 끌어온 뒤 변수로 분기"** 하는 2단계 방식. 조건 분기가 직접 읽을 수 있는 상태가 제한적이기 때문.

## 5. 메시지 시스템

### 5.1 역할 분담 (로직/표시 분리가 잘 된 부분)
- `Game_Message` (상태, rpg_objects): 텍스트 줄 배열, 얼굴 이미지, 배경·위치, 선택지 배열·기본값·취소값·위치·배경, 숫자입력/아이템선택 설정, 스크롤 모드, **선택 결과 콜백**. 그리고 `isBusy()`.
- `Window_Message` (표시, rpg_windows): `$gameMessage`를 매 프레임 폴링해서 텍스트가 있으면 창을 열고 글자를 그린다. 끝나면 입력 대기 → `terminateMessage`에서 `$gameMessage.clear()`.
- 인터프리터는 `$gameMessage`에 내용을 채우고 `'message'` 대기 모드로 들어갈 뿐, 창을 직접 조작하지 않는다.
- 선택 결과는 `Window_ChoiceList` → `$gameMessage.onChoice(n)` → 인터프리터가 등록한 콜백 → `_branch[indent] = n`.
- 전투 중 `BattleManager`도 `$gameMessage.add`로 승리/보상 메시지를 띄운다. 즉 **메시지 큐는 전역 단일 자원**.

### 5.2 화자 이름
- MV의 101 명령에는 **이름 필드가 없다**(params는 얼굴 파일, 얼굴 인덱스, 배경, 위치 4개뿐; `command101`). 화자 이름은 본문 첫 줄에 직접 쓰거나 `\N[n]`(액터 이름)로 넣는 것이 관례이고, 이름 창은 플러그인 영역이었다.
- (참고) 후속작 MZ에서 101에 화자 이름 파라미터가 추가되었다 **(소스 외 지식, 본 저장소로 확인 불가)**.

### 5.3 제어 문자
처리는 두 단계로 나뉜다.

**① 사전 치환 (`Window_Base.convertEscapeCharacters`)** — 그리기 전에 문자열 자체를 바꿈
| 문자 | 의미 |
|---|---|
| `\V[n]` | 변수 n의 값 (두 번 치환해서 `\V[\V[1]]` 같은 1단계 중첩 지원) |
| `\N[n]` | 액터 n의 이름 |
| `\P[n]` | 파티 n번째 멤버 이름 |
| `\G` | 통화 단위 |
| `\\` | 역슬래시 자체 |

**② 그리면서 처리 (`Window_Base.processEscapeCharacter` / `Window_Message.processEscapeCharacter`)** — 글자 진행 중 상태 변화
| 문자 | 의미 |
|---|---|
| `\C[n]` | 글자색 (창 스킨 팔레트 인덱스) |
| `\I[n]` | 아이콘 그리기 |
| `\{` / `\}` | 글자 크게/작게 |
| `\$` | 소지금 창 열기 |
| `\.` | 15프레임 대기 |
| `\|` | 60프레임 대기 |
| `\!` | 입력 대기(클릭할 때까지 멈춤) |
| `\>` / `\<` | 이 줄 순간 표시 시작/끝 |
| `\^` | 문장 끝에서 입력 대기 없이 바로 닫기 |
| `\S[n]` | 글자 표시 속도 변경 — **community 버전 추가 기능으로 보임** (`_textSpeed` 필드, 원본 1.6.1에는 없던 것으로 추정) |

- 페이지 넘김: 내부적으로 `\f`(form feed)를 넣어 새 페이지를 강제(`Game_Message.newPage`). 창 높이(4줄)를 넘으면 자동 새 페이지(`needsNewPage`).

### 5.4 텍스트 표시와 대기 흐름
1. 101 실행 → 401 줄들을 `$gameMessage`에 모두 추가, 바로 뒤의 선택지/숫자입력도 함께 세팅 → 인터프리터는 message 대기.
2. `Window_Message.update`: 창이 열려 있지 않으면 `startMessage`(제어 문자 치환, 위치·배경 적용, 열기).
3. `updateMessage`: 프레임당 1글자 출력(속도 카운터 있음). 결정/취소/터치 입력이 들어오면 `_showFast`로 남은 글자를 한 번에 표시(`updateShowFast`).
4. 글이 끝나면(`onEndOfText`) 선택지 등 입력이 있으면 해당 서브 창 시작, 없으면 **pause(클릭 대기)**. `\^`가 있었으면 바로 종료.
5. 클릭 → `terminateMessage` → `$gameMessage.clear()` → `isBusy()`가 false가 됨 → 인터프리터 다음 명령 진행.
6. 연속 101에서 설정(배경·위치)이 같으면 창을 닫지 않고 이어서 표시(`doesContinue`, `areSettingsChanged`) — 깜빡임 방지.

- 선택지 취소 처리: 취소값 -1이면 취소 불가, -2면 "취소 분기(403)", 0 이상이면 해당 선택지로 간주(`Window_ChoiceList.isCancelEnabled`, `setupChoices`).
- 자동 진행(오토 모드), 스킵(기읽음 스킵), 백로그, 보이스 동기화 기능은 **없다**.

## 6. 비주얼노벨식 에피소드 연출 에디터에 적용

전제: 타일맵/필드 이동 없음. 에피소드 = 대사 + CG(배경·스탠딩·이벤트 CG) + BGM/SE + 선택지/분기 + 일부 게임 상태(플래그, 호감도, 카드 지급, 전투 진입).

### 6.1 가져올 것 (구조가 검증된 부분)
1. **"명령 배열 + 협력형 인터프리터" 모델 자체.** 매 프레임 `update()`, 명령이 계속/양보를 반환, 카운트 대기와 폴링 대기의 두 종류 — 이 단순한 모델이 저장·재개, 스킵, 디버그 스텝 실행에 모두 유리하다.
2. **연출 상태와 표시 분리.** `Game_Message`/`Game_Screen`/`Game_Picture`처럼 "순수 상태 객체 + 매 프레임 그것을 읽는 뷰". 인터프리터는 상태만 바꾸고 뷰는 폴링. 테스트·헤드리스 실행·리플레이가 쉬워진다.
3. **명령 = `type + 파라미터`의 데이터, 실행기 = 타입별 핸들러 테이블.** 모르는 명령 무시, 핸들러 등록만으로 확장.
4. **분기 결과 저장 방식**: 선택지/조건/전투 결과를 "분기 슬롯"에 기록하고 케이스가 읽는 방식(`_branch`). 트리 구조로 바꾸더라도 "전투 결과로 분기" 같은 패턴은 그대로 유용.
5. **공통 이벤트 = 서브루틴 호출(자식 인터프리터, 깊이 제한).** 반복 연출(예: "캐릭터 등장 연출", "카드 획득 연출")을 재사용 단위로.
6. **실행 전 리소스 스캔(`requestImages`).** 에피소드 시작 전에 리스트를 훑어 CG·음원을 프리로드. 에디터에서는 "누락 리소스 검사"로도 재사용 가능.
7. **에러에 출처(에피소드 ID, 명령 줄 번호) 붙이기.**
8. **"완료까지 대기" 옵션을 연출 명령마다 두는 UX.** 연출 시간 = 대기 시간으로 자연스럽게 연결.
9. **스위치(boolean) / 변수(number) 이원화 + 이름 붙은 ID.** 단, ID 대신 문자열 키 고려(아래).
10. **텍스트 내 인라인 제어 문자 개념**(변수 삽입, 색, 순간 대기, 클릭 대기). 단 문법은 재설계.

### 6.2 바꿀 것
| MV 방식 | 문제 | 제안 |
|---|---|---|
| 평평한 배열 + indent | 에디터 외에는 편집·diff·머지가 어렵고, indent가 깨지면 의미가 깨짐 | **저장 형식은 트리(블록 중첩 JSON)** 로, 런타임에서 평탄화하거나 트리 그대로 스택 기반 실행. git diff 친화성 중요(1인 개발 + 버전 관리) |
| 위치 기반 `parameters` 배열 | `params[3]`이 무슨 의미인지 코드 없이 모름. 버전 업 시 호환 지옥 | **이름 있는 필드 객체** + 명령별 스키마(JSON Schema 등)로 검증 |
| 숫자 코드 (101, 231…) | 가독성 없음 | 문자열 타입(`say`, `show_cg`, `play_bgm`…) |
| 101 + 401 연속 행 | 줄 단위로 쪼개진 대사 | **대사 1개 = 명령 1개**(화자, 표정, 본문, 보이스 파일 필드) |
| 화자 이름 없음 / 얼굴 이미지 고정 | VN에 부적합 | 화자(캐릭터 ID) + 표정 키 + 표시 이름 오버라이드. 화자 선택 시 스탠딩 하이라이트 등 자동 연출 연결 |
| 그림 번호 1~100 슬롯 | "몇 번이 누구였지?" 문제 | **이름 있는 레이어/슬롯**(`bg`, `char_left`, `char_center`, `cg`, `fx`) + 캐릭터 ID로 스탠딩 참조 |
| 선형 보간만 존재 | 연출 품질 한계 | 이징 함수 선택, 크로스페이드(배경 전환), 트랜지션 프리셋(fade/dissolve/slide) |
| 오디오 명령은 즉시 반환 | 페이드 대기 수동 처리 | 오디오에도 "완료까지 대기" 옵션, BGM 크로스페이드, 보이스 채널 추가 |
| 스위치/변수 숫자 ID | 이름 변경·삭제 시 추적 어려움 | 문자열 키 + 선언 테이블(타입, 기본값, 설명) + **사용처 역참조**(에디터에서 "이 플래그를 쓰는 곳") |
| 페이지 조건 고정 AND 슬롯 | 표현력 부족 | 에피소드 해금 조건은 **조건식 트리(AND/OR/NOT + 비교)** 하나로 통일. 조건 분기 명령과 같은 평가기 공유 |
| 제어 문자 `\C[n]` 등 | 학습 비용, 오타 감지 불가 | 태그형 마크업(예: `{color=red}...{/color}`, `{wait=0.5}`, `{var:affinity}`)과 에디터 미리보기·린트 |
| 프레임 단위 대기 | 60fps 고정 가정 | 시간(초/ms) 단위. 내부적으로 delta time 누적 |
| `$gameMessage` 전역 단일 | 병렬 연출 충돌 | VN에선 대사 채널은 하나로 충분하지만, **누가 대사 채널을 점유하는지 명시적 소유권** 부여 |
| 메시지 기능 | 오토/스킵/백로그/보이스 없음 | VN 필수 기능으로 런타임에 내장: 오토 모드, 기읽음 스킵(대사 ID별 읽음 기록 필요 → 대사에 **안정 ID** 부여), 백로그, 보이스 재생·정지 동기화 |
| 레이블 점프(119) | 스파게티 흐름 | 에피소드 내부는 블록 구조, 에피소드 간 이동은 "다음 에피소드/장면" 명령으로 명시 |

추가로 권장:
- **"스킵 시 최종 상태 계산"** 이 가능하도록 연출 명령을 "목표 상태 지정형"으로 설계(MV의 232처럼 목표값+시간). 그러면 스킵 = 모든 진행 중 트윈을 즉시 완료로 처리하면 된다.
- 세이브는 **"명령 위치 + 연출 상태 스냅샷(현재 배경/스탠딩/BGM)"** 저장. MV처럼 인터프리터 객체를 통째로 직렬화하기보다, 명령에 안정 ID를 두고 그 ID로 재개하는 편이 에피소드 데이터 수정 후에도 세이브가 덜 깨진다.
- 선택지에 **조건부 표시/비활성**(플래그·카드 보유 조건) 필드. MV는 선택지 조건이 없어 플러그인 영역이었다.

### 6.3 버릴 것
- 맵·캐릭터·탈것·이동 루트·말풍선·타일셋·원경·날씨·조우 관련 명령 전부(3.4 절, 136/140/202/206/236/282/284/285 등).
- 상점(302), 이름 입력(303), 숫자 입력(103), 아이템 선택(104) — 게임 UI 쪽 기능이지 에피소드 연출 명령이 아님(필요 시 "게임 UI 열기" 하나로 추상화).
- 액터 장비/직업/레벨/경험치/능력치 직접 조작 명령(315~321) — 카드 수집형에서는 "카드 지급", "보상 지급" 같은 도메인 명령 몇 개로 대체.
- 스크립트(355)와 조건/변수의 스크립트 `eval` — 1인 개발 툴이라도 **임의 코드 실행은 데이터 검증·저장 호환성을 무너뜨린다**. 대신 "커스텀 명령(코드에 등록된 핸들러) + 파라미터 스키마" 방식의 화이트리스트 확장.
- 플러그인 명령(356)의 "공백 split 문자열" 방식 — 위 커스텀 명령으로 흡수.
- 셀프 스위치 — 맵 이벤트가 없으므로 의미가 줄어든다. 대신 **에피소드별 지역 변수(에피소드 스코프)** 개념으로 대체(예: "이 에피소드에서 선택지 A를 골랐는가").
- 병렬 이벤트 / 병렬 공통 이벤트의 "스위치 ON 동안 무한 반복" 모델 — VN 에피소드에서는 필요성 낮고 버그의 근원. 필요하면 "백그라운드 연출 트랙(예: 반복 흔들림, 비 효과)"으로 명시적 시작/정지.
- 숫자 슬롯 그림 100개 + 전투용 오프셋 같은 암묵 규칙.

### 6.4 최소 명령 세트 초안 (참고용)
| 분류 | 명령 |
|---|---|
| 대사 | `say`(화자, 표정, 본문, 보이스), `narrate`, `choice`(옵션별 조건·블록), `wait`, `wait_click` |
| 캐릭터 | `char_show`/`char_hide`/`char_move`/`char_expression` (위치 슬롯, 트랜지션, 대기) |
| 배경·CG | `bg_change`(트랜지션), `cg_show`/`cg_hide`(갤러리 해금 플래그 자동 기록) |
| 화면 | `fade`, `flash`, `shake`, `tint` (모두 이징 + 대기 옵션) |
| 오디오 | `bgm_play`(크로스페이드)/`bgm_stop`, `se_play`, `ambient_play`/`stop`, `voice_play` |
| 흐름 | `if`/`else`(조건식 트리), `call`(공통 시퀀스), `goto_episode`, `end` |
| 상태 | `set_flag`, `set_var`(연산), `give_card`, `give_reward` |
| 연결 | `battle`(편성 ID, 결과별 블록: win/lose/escape), `open_ui` |

이 표는 MV의 분류를 VN 용도로 재구성한 **설계 제안**이며 MV 소스에 있는 것이 아니다.
