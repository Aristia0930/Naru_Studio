## 0. 한 줄 요약

MV 전투는 **"전원 커맨드 입력 → 속도순 정렬 → 한 명씩 행동 → 턴 종료 처리"** 의 고전 턴제(사이드뷰/프론트뷰 공통)다. 계산 로직(`Game_Action`, `Game_Battler*`)은 비교적 순수한 객체에 모여 있지만, 진행 관리자(`BattleManager`)가 로그 창·상태 창·스프라이트셋의 "바쁨" 상태와 전역 오디오/씬 매니저에 직접 묶여 있어 **그대로는 헤드리스 시뮬레이터가 안 되고, 몇 개의 스텁을 끼우면 된다** 수준이다. 난수는 전부 `Math.random`이고 데미지 공식은 `eval`이라 **서버 검증용 결정론은 보장되지 않는다.**

## 1. 구성 요소와 책임

| 계층 | 클래스 | 책임 |
|---|---|---|
| 진행 | `BattleManager` (정적 싱글턴) | 페이즈 상태 머신, 행동 순서, 행동 실행 순서 제어, 승패 판정, 보상 |
| 행동 | `Game_Action` | "누가 무엇을 누구에게"의 한 건. 대상 산출, 명중/회피/치명, 데미지, 효과 적용, AI 평가 |
| 결과 | `Game_ActionResult` | 대상 1명이 이번 행동으로 받은 결과(빗나감·회피·치명·HP/MP/TP 변화·추가/해제된 상태·버프). 표시 계층이 읽어감 |
| 전투원 | `Game_BattlerBase` → `Game_Battler` → `Game_Actor` / `Game_Enemy` | 능력치, 특성(trait) 집계, 상태·버프·턴 카운트, 행동 슬롯, 비용 지불, 연출 요청 플래그 |
| 집단 | `Game_Unit` → `Game_Party` / `Game_Troop` | 멤버 목록, 생존/사망, 무작위 대상(狙われ率), 대리(감싸기), 전투 이벤트(Troop) |
| 화면 | `Scene_Battle`, `Window_*`, `Spriteset_Battle`, `Sprite_*` | 입력 창, 로그 텍스트, 데미지 팝업, 모션, 애니메이션 |

## 2. BattleManager 상태 머신

### 2.1 페이즈 (`_phase`)
```
init ──setup()──▶ (Scene_Battle.start → startBattle) ──▶ start
start ──startInput()──▶ input
input ──(모든 액터 입력 완료 / 기습당함 / 입력 가능 액터 없음)── startTurn() ──▶ turn
turn ──(행동할 배틀러 있음) startAction()──▶ action
action ──(대상 리스트 소진) endAction()──▶ turn
turn ──(남은 배틀러 없음) endTurn()──▶ turnEnd
turnEnd ──updateTurnEnd()=startInput()──▶ input
(어느 시점이든) 승리/패배/도주/중단 ──endBattle()──▶ battleEnd ──updateBattleEnd()──▶ null(씬 종료)
abort() ──▶ aborting ──checkAbort()──▶ battleEnd
```
- 도식은 `BattleManager.update`의 switch와 각 `startXxx/endXxx`의 `_phase` 대입을 정리한 것.
- `input` 페이즈에는 `update`에 분기가 없다. 입력은 **Scene_Battle의 창들이 사용자 조작으로 진행**시키고, 끝나면 `BattleManager.selectNextCommand` → 마지막 액터 다음이면 `startTurn`.

### 2.2 매 프레임 진행 조건
`BattleManager.update` 는 다음이 모두 거짓일 때만 페이즈 처리를 한다.
1. `isBusy()` — `$gameMessage.isBusy()` 또는 **스프라이트셋이 바쁨**(애니메이션·모션 재생 중) 또는 **로그 창이 바쁨**(메서드 큐가 남음).
2. `updateEvent()` — start/turn/turnEnd 페이즈에서
   - 강제 행동(명령 339)이 대기 중이면 그것을 즉시 처리(`processForcedAction`)하고 이번 프레임 종료.
   - 아니면 전투 이벤트 인터프리터 갱신 → 이벤트 실행 중이거나 `checkBattleEnd()`가 참이면 종료 → 새 전투 이벤트 페이지 시작 시도(`$gameTroop.setupBattleEvent`).
   - 그 외 페이즈에선 `checkAbort()`만.
- 결과적으로 **로직은 "한 걸음 계산 → 연출이 끝날 때까지 정지 → 다음 걸음"** 의 락스텝으로 진행된다. 각 걸음의 계산 자체는 즉시 끝난다.
- `Scene_Battle.updateBattleProcess`는 입력 창이 활성 상태가 아닐 때(또는 중단/종료 중일 때)만 `BattleManager.update`를 부른다.

### 2.3 전투 시작
- `setup(troopId, canEscape, canLose)`: 멤버 초기화, 적 그룹 구성(`$gameTroop.setup`), 화면의 전투용 그림 초기화, 도주 확률 계산.
- `onEncounter`: 선제(preemptive)/기습(surprise) 확률. 파티 민첩 vs 적 민첩(`Game_Party.ratePreemptive/rateSurprise`). 호출처는 맵 랜덤 조우(`Game_Player.js`)뿐이라 이벤트 전투(301)에서는 선제/기습이 발생하지 않는다.
- `startBattle`: 시스템/파티/적의 `onBattleStart`(TP 초기화, 상태 정리 등) → 출현 메시지를 `$gameMessage`에 추가.

### 2.4 입력 페이즈
- `startInput`: 파티·적 전원 `makeActions()`(행동 슬롯 생성; 적은 이 시점에 AI로 행동 결정). 기습당했거나 입력 가능한 액터가 없으면 바로 `startTurn`.
- 행동 슬롯 수 `makeActionTimes`: 기본 1 + "행동 횟수 추가" 특성 각각을 확률로 굴려 +1.
- 액터별로 슬롯을 순서대로 채운다(`selectNextCommand`/`selectPreviousCommand`, 액터 내부의 `_actionInputIndex`). 자동 전투 특성이면 `makeAutoBattleActions`(평가값 최고 행동 자동 선택), 혼란이면 `makeConfusionActions`.
- 화면 쪽은 `BattleManager.inputtingAction()`이 돌려주는 `Game_Action`에 `setSkill/setItem/setTarget`만 호출한다 → **입력 소스(사람/AI/네트워크)를 바꾸기 쉬운 이음매**.

### 2.5 행동 순서 (속도 계산)
- `startTurn` → `makeActionOrders`: 기습이면 파티 제외, 선제면 적 제외. 각 배틀러 `makeSpeed()` 후 **속도 내림차순 정렬**.
- 행동 1건의 속도(`Game_Action.speed`): `민첩 + 난수(0 ~ floor(5 + 민첩/4) - 1)` + 스킬/아이템의 속도 보정 + (일반 공격이면 "공격 속도" 특성).
- 배틀러 속도(`Game_Battler.makeSpeed`): 자기 행동 슬롯들 중 **가장 느린 값**. (여러 번 행동하는 배틀러는 가장 느린 행동 기준으로 한 번에 몰아서 행동)
- 순서는 **턴 시작 시 한 번 확정**된다. 턴 도중 민첩 버프가 걸려도 이번 턴 순서는 안 바뀜. 리스트에서 꺼낼 때(`getNextSubject`) 사망·전투 이탈한 배틀러는 건너뜀.

### 2.6 행동 처리 (turn ↔ action)
`processTurn`(turn 페이즈, 현재 주체 `_subject` 기준):
1. 현재 행동 슬롯을 꺼냄 → `prepare()`(혼란 시 강제 공격 등) → `isValid()`(사용 가능 여부: 비용, 봉인, 행동 가능 상태)면 `startAction`. 무효면 그냥 버림. 슬롯 제거.
2. 남은 슬롯이 없으면 `onAllActionsEnd()`(아래 4.1의 "행동 종료 시" 해제 처리) → 다음 주체.

`startAction`:
- 대상 산출(`makeTargets`) → 비용 지불·아이템 소모(`useItem`) → **전역 효과 적용**(`applyGlobal`: 효과 중 "공통 이벤트"를 예약) → 로그 창에 시작 연출 지시 → 페이즈 `action`.

`updateAction`(action 페이즈, 프레임마다 대상 1명씩):
- `invokeAction(subject, target)`: 순서대로 확률 판정
  1. **반격**(`itemCnt`: 물리 공격이고 대상이 행동 가능하면 대상의 반격률) → 대상이 주체에게 일반 공격.
  2. **마법 반사**(`itemMrf`: 마법 공격이면 대상의 반사율) → 같은 행동을 주체에게 적용.
  3. 그 외 **일반 적용**: 대리 판정(`applySubstitute`: 대상이 빈사(HP 1/4 미만)이고 필중이 아니면 "감싸기" 특성 아군이 대신 맞음) → `action.apply(realTarget)`.
- 대상이 다 떨어지면 `endAction` → turn 페이즈 복귀.
- 연속 공격(repeats)은 **대상을 반복 횟수만큼 복제한 리스트**로 구현(`repeatTargets`). 무작위 대상 N회는 `numTargets` 만큼 랜덤 추첨.

### 2.7 턴 종료
`endTurn` → 전원 `onTurnEnd()`:
- 결과 초기화 → **재생**(HP/MP/TP 재생률, `regenerateAll`, 생존자만)
- 상태 턴 수와 버프 턴 수 1 감소(단, 강제 행동으로 발생한 "강제 턴"이면 감소 안 함)
- "턴 종료 시" 자동 해제 타이밍의 만료 상태 해제(`removeStatesAuto(2)`)
- 선제/기습 플래그 해제. 다음 프레임 `updateTurnEnd` → 다시 `startInput`.
- 턴 카운트는 `startTurn`에서 `$gameTroop.increaseTurn()`으로 증가(= 턴 **시작** 시점에 증가). 전투 이벤트의 "턴 종료" 조건 페이지는 turnEnd 페이즈 동안 실행된다.

### 2.8 전투 종료
- `checkBattleEnd`: 중단 체크 → 파티 전멸이면 `processDefeat` → 적 전멸이면 `processVictory`.
- 승리: 전투 한정 상태 해제, 승리 연출·ME, 원래 BGM 복귀, 보상 계산(`makeRewards`: 골드·경험치 합계, 적별 드롭 테이블 추첨) → 메시지 → 지급 → `endBattle(0)`.
- 도주(`processEscape`): 선제면 무조건 성공, 아니면 `0.5 × 파티 민첩 / 적 민첩` 확률. 실패 시 확률 +0.1 누적, 파티 행동 취소 후 **적만 행동하는 턴**으로 진행.
- `endBattle(result)`: 0승/1도주(중단)/2패. 이벤트 콜백으로 결과 전달(이벤트 명령 301의 분기). 패배 허용 아니면 게임오버 씬.

## 3. 데미지와 판정 (`Game_Action.apply`)

### 3.1 판정 순서
1. **적용 가능성** `testApply`: 대상의 생사가 "사망자 대상" 여부와 맞아야 함 + (전투 중이면 그 외 조건 무시).
2. **명중** `itemHit`: 물리면 `스킬 성공률 × 주체 명중률(hit)`, 그 외는 `성공률`만. 실패 → `missed`.
3. **회피** `itemEva`: 물리면 대상 회피율(eva), 마법이면 마법 회피율(mev), 필중이면 0. → `evaded`.
4. 명중 시
   - 데미지 타입이 있으면 **치명타** `itemCri`: 스킬에 치명 허용일 때 `주체 치명률(cri) × (1 - 대상 치명 회피율(cev))`.
   - **데미지 계산** `makeDamageValue` → **적용** `executeDamage`.
   - **효과 목록** 순서대로 적용(`applyItemEffect`).
   - **사용자 효과**: 스킬의 TP 획득량 × 주체 TP 충전률(tcr)을 주체에게(`applyItemUserEffect`).

### 3.2 데미지 공식 파이프라인 (`makeDamageValue`)
1. **기본값**: 스킬마다 문자열 공식(예: `a.atk * 4 - b.def * 2`)을 `eval`로 계산(`evalDamageFormula`). `a`=주체, `b`=대상, `v`=변수 배열. 음수는 0으로 자른 뒤 회복 타입(3,4)이면 부호 반전. 예외나 NaN은 0.
2. × **속성 배율** `calcElementRate`: 스킬 속성이 "일반 공격(-1)"이면 주체의 공격 속성들 중 **대상에게 가장 유리한(최대) 배율**, 아니면 그 속성 하나의 대상 배율(`elementRate` = 해당 속성 특성 값들의 **곱**).
3. × 물리면 대상 **물리 데미지율(pdr)**, 마법이면 **마법 데미지율(mdr)**.
4. 회복이면 × 대상 **회복 효과율(rec)**.
5. 치명이면 **×3** (`applyCritical`, 상수).
6. **분산** `applyVariance`: ±(|값| × 분산%/100). 두 개의 균등 난수 합이라 **삼각 분포**(중앙값에 몰림).
7. **방어** `applyGuard`: 대상이 방어 중이고 양수 데미지면 `÷ (2 × 방어 효과율 grd)`.
8. 반올림.

적용(`executeDamage` → `executeHpDamage`): 흡수면 대상 현재 HP로 상한 → HP 감소 → 양수면 `onDamage`(데미지로 풀리는 상태 해제 판정, 받은 비율 × 50 × tcr 만큼 TP 충전) → 흡수면 주체(반사 시 반사한 대상) 회복. MP도 동일 구조. 데미지 0이면 치명 표시 취소.

### 3.4 상태 부여/해제
- 부여 확률(`itemEffectAddNormalState`): `효과 확률 × 대상 상태 유효도(stateRate, 특성 곱) × 운 보정`. 필중 타입이면 효과 확률 그대로.
- **운 보정** `lukEffectRate`: `max(1 + (주체 운 - 대상 운) × 0.001, 0)`. 운 100 차이 = ±10%.
- 실제 부여(`Game_Battler.addState` → `isStateAddable`): 생존 중, 상태 무효 특성 없음, **이번 행동에서 막 해제된 상태가 아님**, "행동 제약으로 해제" 상태인데 이미 행동 제약 중이 아님. 이미 걸린 상태면 **턴 수만 재설정**(중첩 없음).
- 전투불능(death state, 기본 ID 1)도 일반 상태로 구현: 부여 시 `die()`, 해제 시 `revive()`.
- 상태 지속 턴: 부여 시 `minTurns ~ maxTurns` 랜덤(`resetStateCounts`).
- 자동 해제 타이밍 `autoRemovalTiming`: 0 없음 / 1 **행동 종료 시**(주체의 모든 행동 후, `onAllActionsEnd`) / 2 **턴 종료 시**(`onTurnEnd`). 턴 카운트 감소는 타이밍과 무관하게 턴 종료에 한 번.
- 기타 해제: 데미지로 해제(확률), 행동 제약 발생 시 해제(`onRestrict`), 걸음 수(맵), 전투 종료 시 해제.
- **행동 제약(restriction)**: 걸린 상태 중 최대값. 0 없음 / 1 적 공격 / 2 아무나 공격 / 3 아군 공격 / 4 행동 불가. 1~3은 혼란(`confusionTarget`), 4는 `canMove()` false. 제약이 새로 걸리면 그 즉시 예약 행동이 취소된다.
- 버프: 단계 ±2, 단계당 ±25%(`paramBuffRate`), 별도 턴 카운트.

### 3.5 특성(Trait) 시스템 — MV 전투의 실질적 핵심
- 모든 수치 보정은 "특성 객체"의 목록에서 집계한다(`traitObjects`): 액터 = 액터 + 직업 + 장비 + 상태, 적 = 적 + 상태.
- 특성 = `{code, dataId, value}`. 집계 방식이 코드별로 정해져 있다.
  - **곱(traitsPi)**: 속성 유효도(11), 약화 유효도(12), 상태 유효도(13), 능력치 배율(21), 특수 능력치(sparam, 23).
  - **합(traitsSum)**: 추가 능력치(xparam, 22: 명중·회피·치명·치명회피·마법회피·마법반사·반격·HP/MP/TP 재생).
  - **집합(traitsSet)**: 상태 무효(14), 공격 속성(31), 공격 시 상태(32), 스킬 타입 추가/봉인, 스킬 추가/봉인, 장비 관련, 행동 횟수 추가(61), 특수 플래그(62: 자동전투/방어/감싸기/TP 이월), 소멸 효과(63), 파티 능력(64).
- 능력치 최종값(`param`): `(기본 + 영구 증가) × 능력치 배율(특성 곱) × 버프 배율`, 상하한 클램프 후 반올림.
- 특수 능력치(sparam): 狙われ率(tgr), 방어 효과율(grd), 회복 효과율(rec), 약학(pha), MP 소비율(mcr), TP 충전률(tcr), 물리/마법/바닥 데미지율(pdr/mdr/fdr), 경험치 획득률(exr).
- **대상 무작위 선택**(`Game_Unit.randomTarget`): 생존자들의 tgr 가중치 룰렛.

## 4. 적 AI

### 4.1 행동 패턴 (`Game_Enemy.makeActions`)
적 데이터의 `actions` 배열 각 항목: `skillId`, `conditionType`, `conditionParam1/2`, `rating`(1~9).
1. 조건 검사(`meetsCondition`) + 사용 가능(`canUse`)한 항목만 남김.
   - 조건 타입: 0 항상 / 1 턴(`A + B×n`, B=0이면 A턴 정확히) / 2 HP 비율 범위 / 3 MP 비율 범위 / 4 상태 걸림 / 5 파티 최고 레벨 이상 / 6 스위치 ON.
2. **rating 필터**: 남은 것 중 최고 rating을 `max`라 할 때 `rating > max - 3` 인 것만 후보(`selectAllActions`).
3. **가중 추첨**: 각 후보 가중치 = `rating - (max - 3)`. 즉 최고 rating은 3, 1 낮으면 2, 2 낮으면 1. 행동 슬롯마다 독립 추첨(`selectAction`).
4. 대상은 이 시점에 정하지 않는다. `_targetIndex = -1` 이 기본이므로 실행 시 **tgr 가중 랜덤**(단일 대상 스킬 기준).

### 4.2 평가형 AI (액터 자동전투 전용)
- `Game_Action.evaluate`: 후보 대상마다 `evaluateWithTarget`(HP 데미지 행동만 평가: 적에겐 `예상 데미지 / 대상 현재 HP`, 아군 회복은 `회복량 / 최대 HP`). 전체 대상은 합산, 단일 대상은 최댓값 + 그 대상 index 기억. 반복 횟수 곱 + 0~1 랜덤 노이즈.
- 상태 부여·버프 스킬은 HP 효과가 없으면 평가값이 사실상 0(undefined → 0 처리 **(추정: undefined 합산 시 NaN 가능성 있음, 실제로는 비교에서 탈락)**) → 자동전투가 보조 스킬을 거의 안 쓰는 이유.
- 적에게는 이 평가 AI가 쓰이지 않는다.

### 4.3 평가
- 장점: 에디터에서 **표 하나(스킬 + 조건 + 가중치)** 로 기획자가 패턴을 만들 수 있다. 턴 주기 조건(`A + B×n`)으로 "3턴마다 필살기" 같은 보스 패턴을 데이터만으로 표현.
- 한계: 대상 선택 로직 없음(약점 노리기, 빈사 마무리 불가), 조건 1개만(AND 불가), 행동 간 순서/콤보 불가, 상태 기억 없음 → 정교한 보스는 전투 이벤트(Troop page) + 강제 행동(339)으로 보완하는 것이 MV 관례.

## 5. 전투 이벤트 (Troop page)

- 적 그룹 데이터에 **페이지 목록** `{conditions, span, list}`. 실행기는 `Game_Troop._interpreter`(이벤트 명령 인터프리터 재사용; 03 문서 참조).
- 조건(`Game_Troop.meetsConditions`, 모두 AND, 하나도 없으면 실행 안 함): 턴 종료 시 / 턴 `A + B×n` / 적 n번 HP ≤ x% / 특정 액터 HP ≤ x% / 스위치.
- `span`: 0 전투 1회, 1 턴 1회(턴 증가 시 플래그 리셋), 2 순간(조건 만족하면 매번 — 플래그를 세우지 않음).
- 실행 시점: `BattleManager.updateEventMain`이 start/turn/turnEnd 페이즈에서 호출 → **행동과 행동 사이**(turn 페이즈에서 다음 주체로 넘어가기 전 프레임들)와 턴 종료 시에 끼어든다. action 페이즈(대상별 적용 중)와 input 페이즈 중에는 실행되지 않는다.
- 페이지는 앞에서부터 검사해 **첫 번째로 조건을 만족하고 아직 안 돈 페이지 하나**만 시작. 실행 중엔 전투 진행이 멈춘다.
- 예약 공통 이벤트(스킬 효과 44)가 페이지보다 우선.
- 전투 이벤트에서 쓰는 명령: 메시지, 적 HP·상태 조작, 적 출현/변신, 강제 행동(339), 전투 중단(340), 스위치·변수 등. 강제 행동은 `BattleManager.forceAction`이 행동 순서 리스트에서 그 배틀러를 빼고 즉시 행동시키며(`processForcedAction`), 이때의 턴은 "강제 턴"으로 상태 턴 감소를 건너뛴다.
- 비고: 대사·연출이 전투 이벤트로 들어가므로 **스토리 연출 시스템과 전투 시스템이 같은 인터프리터를 공유**한다는 점이 MV 설계의 실용적 장점.

## 6. 로직과 화면의 분리도 평가

### 6.1 잘 분리된 부분
| 항목 | 근거 |
|---|---|
| 계산 로직의 위치 | 명중·데미지·상태·특성 집계가 전부 `Game_Action`/`Game_Battler*`에 있고 Sprite/Window를 참조하지 않는다 |
| 결과 객체 | 계산 결과를 `Game_ActionResult`에 남기고, 표시(`Window_BattleLog.displayActionResults`)가 **나중에 읽어서** 텍스트·팝업·모션 큐를 만든다 |
| 연출 요청을 플래그로 | `Game_Battler.requestEffect/requestMotion/startAnimation/startDamagePopup`은 필드만 세팅하고, 스프라이트가 폴링해서 소비(pull 방식) |
| 입력 이음매 | 화면은 `Game_Action`에 스킬·대상만 채움. 적 AI도 같은 객체를 채움 |
| 상태 소유 | 전투 상태는 전역 게임 객체(`$gameParty`, `$gameTroop`)에 있어 화면 없이도 존재 |

### 6.2 결합된 부분 (헤드리스 실행의 장애물)
| 결합 | 위치 | 영향 |
|---|---|---|
| 진행이 연출 완료를 기다림 | `BattleManager.isBusy` → `_spriteset.isBusy()`, `_logWindow.isBusy()` | 로그 창/스프라이트셋이 없으면 null 참조 오류. 스텁 필요 |
| 매니저가 창을 직접 호출 | `_logWindow.startAction/displayXxx/push`, `_statusWindow.refresh` (BattleManager 곳곳) | 로직 흐름 안에 표시 호출이 섞여 있음 |
| 메시지 큐 사용 | 출현·승리·보상·도주 메시지를 `$gameMessage.add` | 메시지 창이 소비하지 않으면 `isBusy`가 영원히 참 |
| 오디오·씬 | `playVictoryMe`, `replayBgmAndBgs`(AudioManager), `updateBattleEnd`(SceneManager), `Game_Battler.performMiss` 등의 SoundManager, 액터 피격 시 `$gameScreen.startShake` | 순수 계산 중에도 사운드/화면 호출 발생 |
| 전역 싱글턴 | `$gameParty`, `$gameTroop`, `$gameSwitches`, `$gameVariables`, `$gameTemp`, `$dataSkills/States/...`, `BattleManager` 자체가 정적 클래스 | 동시에 여러 전투 시뮬레이션 불가(병렬 몬테카를로 X), 테스트 격리 어려움 |
| 난수 | 모든 판정이 `Math.random`/`Math.randomInt` 직접 호출 | **시드 고정 불가 → 재현·리플레이·서버 검증 불가** |
| 데미지 공식 `eval` | `Game_Action.evalDamageFormula` | 임의 코드 실행. 서버에서 그대로 돌리기엔 보안·결정론 문제. 공식에서 `v`(전역 변수)를 읽을 수 있어 외부 상태 의존 |
| 데이터 직접 참조 | `$dataStates[stateId]` 등 전역 DB 배열 | 주입 불가 |
| 프레임 진행 | 대상 1명당 최소 1프레임, 연출 대기 | 시뮬레이션 속도 제약(스텁으로 isBusy=false면 해소) |

### 6.3 순수 로직으로 떼어낼 수 있는가?
- **계산 핵심(`Game_Action` + `Game_Battler*` + `Game_Unit`)**: 전역 데이터 배열과 `$gameParty/$gameTroop`만 채우면 Node에서 돌릴 수 있다 **(추정: 실제 구동 테스트는 하지 않음. 정적 의존성 분석 기준)**. SoundManager·$gameScreen 호출은 빈 객체로 스텁.
- **진행(BattleManager)**: 로그 창·상태 창·스프라이트셋을 "항상 안 바쁜 빈 객체"로, `$gameMessage`를 즉시 비우는 객체로, AudioManager·SceneManager를 no-op으로 바꾸고, `input` 페이즈를 코드로 채우면 **전투 1판을 루프로 끝까지 돌리는 시뮬레이터는 가능**하다 **(추정)**. 밸런스 테스트(승률·평균 턴 수)용으로는 쓸 만하다.
- **서버 검증**: 현 구조 그대로는 **부적합**. 필수 조건인 (1) 시드 RNG 주입, (2) 행동 입력 로그로 재생했을 때 비트 단위 동일 결과, (3) eval 없는 공식, (4) 인스턴스 단위 상태(전역 X)를 하나도 만족하지 않는다. "구조와 공식은 참고하고 코드는 새로 작성"이 맞다.

## 7. 카드 수집형 턴제 RPG 적용

전제: 플레이어는 수집한 카드(캐릭터/스킬 카드)로 덱·편성을 만들고, 턴제로 싸우며, 스토리 에피소드와 전투가 연결됨. 툴은 카드·적·스킬·상태·전투 편성 데이터를 편집하고, 시뮬레이터로 밸런스를 확인하는 것이 목표라고 가정.

### 7.1 가져올 것
1. **페이즈 상태 머신의 골격**: start → input → turn(행동 순회) → turnEnd → 반복, 그리고 어느 시점이든 battleEnd. 명시적 페이즈 문자열은 디버깅·리플레이 로그에 유리.
2. **"행동(Action) 객체"와 "결과(ActionResult) 객체"의 분리.** 계산은 결과를 만들고, 연출은 결과를 읽는다. 이것을 한 단계 더 밀어 **로직이 이벤트 로그(`[{type:'damage', target, value, critical}, ...]`)를 출력하고 클라이언트가 그 로그를 재생**하는 구조로.
3. **특성(Trait) 시스템**: `{code, dataId, value}` + 코드별 집계 규칙(곱/합/집합). 카드·장비·상태·패시브·세트 효과를 전부 "특성 보유 객체"로 통일하면 수치 보정 로직이 한 곳에 모인다. 카드 수집형에서 가장 재사용 가치가 큰 부분.
4. **효과(Effect) 목록 방식의 스킬**: "데미지 1개 + 효과 N개(상태 부여, 버프, 회복…)". 데이터 주도 스킬 설계의 기본.
5. **데미지 파이프라인 순서**: 기본 공식 → 속성 → 물리/마법 감쇄 → 치명 → 분산 → 방어 → 반올림. 순서를 고정하고 각 단계를 이름 있는 함수로 둔 점.
6. **상태의 데이터 필드**: 지속 턴 범위, 자동 해제 타이밍(행동 후/턴 종료), 데미지로 해제 확률, 행동 제약 등급, 상태 내 특성. 그대로 차용 가능.
7. **적 AI 표(스킬 + 조건 + rating)** 와 **턴 주기 조건 `A + B×n`**. 기획자 친화적. 
8. **전투 이벤트 페이지(조건 + span + 명령 리스트)**: 스토리 연출 인터프리터를 전투 중에도 재사용 → "보스 HP 50%에서 컷신 + 페이즈 전환" 같은 연출을 툴 하나로.
9. **tgr 가중 무작위 대상**(도발/은신을 수치로 표현), 감싸기(대리), 반격/반사 같은 반응 행동 개념.
10. **입력 이음매**: 화면·AI·자동전투·리플레이가 모두 같은 `Action` 객체를 채우는 구조.

### 7.2 바꿀 것
| MV | 문제 | 제안 |
|---|---|---|
| `Math.random` 직접 호출 | 재현 불가 | **시드 RNG를 전투 컨텍스트에 주입**. 판정마다 소비 순서 고정. 리플레이·서버 검증·버그 재현 |
| 정적 `BattleManager` + 전역 `$gameXxx` | 다중 인스턴스 불가 | `Battle` 인스턴스가 상태(양 진영, 턴, RNG, 로그)를 소유. 데이터 DB는 생성자로 주입 |
| 로직이 연출 완료를 기다림(`isBusy`) | 헤드리스 불가 | 로직은 **동기적으로 한 턴(또는 한 행동)을 끝까지 계산**하고 이벤트 로그를 반환. 연출은 로그를 소비. 전투 이벤트(컷신) 지점은 로직이 "일시정지 지점"을 로그에 표시하고 대기 |
| 데미지 공식 `eval` 문자열 | 보안·결정론·타입 검증 불가 | **공식 DSL**(사칙연산 + 제한된 변수 `a.atk`, `b.def`, 상수) 파서, 또는 공식 프리셋 + 계수 필드. 툴에서 미리보기 계산 |
| 치명 ×3 상수, 운 보정 0.001, 버프 25%, 도주 0.5 등 하드코딩 | 밸런스 조정이 코드 수정 | **전투 규칙 상수 테이블**(데이터)로 외부화 |
| 속도 = 민첩 + 랜덤, 턴 시작 시 순서 고정 | 카드 게임에 흔한 "행동 게이지/CT", "속도 버프 즉시 반영", "다음 행동 순서 미리보기"와 안 맞음 | 행동 순서 정책을 교체 가능하게(고정 순서 / 속도순 / CT 게이지). 미리보기 UI가 필요하면 **랜덤 성분 제거 또는 턴 시작 시 공개** |
| 액터 = 액터+직업+장비 고정 구조 | 카드 수집형과 불일치 | 유닛 = 카드 기본 데이터 + 성장(레벨/돌파/각성) + 장착 카드/유물 + 상태. 모두 특성 보유 객체로 |
| 적 AI: 조건 1개, 대상 랜덤 | 단조로움 | 조건식 트리(AND/OR) + **대상 선택 규칙**(최저 HP, 약점 속성, 특정 역할) + 패턴 시퀀스/페이즈(HP 구간별 행동표) |
| 상태 중첩 불가(턴만 갱신) | 카드 게임의 스택형 디버프(중독 n중첩 등) 표현 불가 | 상태별 중첩 정책: 갱신/누적 스택/최대 스택/독립 인스턴스 |
| HP/MP/TP 3자원 고정 | 카드 게임은 코스트·에너지·쿨타임 중심 | 자원 정의를 데이터로(팀 공유 에너지, 개별 쿨다운 등) |
| 전투 이벤트 조건 AND 고정 슬롯 | 표현력 부족 | 에피소드 툴과 같은 **조건식 평가기 공유** |
| 결과 객체가 대상별 마지막 1건만 보관(`clear()` 후 덮어씀) | 다단 히트·연쇄 반응 로그 손실 | 결과는 **append-only 이벤트 로그**로 |
| 보상 계산이 BattleManager 안 | 서버 권한 분리 어려움 | 보상은 전투 결과(승패·턴 수·조건 달성)를 입력으로 받는 별도 서비스. 서버가 판정 |

### 7.3 버릴 것
- `Scene_Battle`/`Window_Battle*`/`Spriteset_Battle`의 창 기반 UI 흐름 전체(파티 커맨드 → 액터 커맨드 → 스킬 창 → 대상 창). 카드 UI는 손패/드래그/타깃팅으로 완전히 다르다.
- `Window_BattleLog`의 "메서드 이름 문자열 큐" 방식(`push('performDamage', target)`). 아이디어(연출을 큐로 순차 재생)는 유지하되 타입 있는 이벤트 로그로 대체.
- 장비 슬롯·무기 타입·방어구 타입·장비 봉인 등 장비 특성(51~55), 경험치/레벨 곡선 처리, 드롭 아이템 테이블의 MV식 구현(가챠/보상 체계는 별도 설계).
- 선제/기습/조우 확률, 맵 걸음 수로 풀리는 상태, 탈것 — 필드 제외 방침과 함께 제거.
- 혼란의 "공격 대상 랜덤화" 3단계 구현 등 세부 규칙(필요하면 상태 효과 하나로 재정의).
- 자동전투 평가 AI(`evaluate`) — HP 효과만 보는 단순 휴리스틱. 오토 전투가 필요하면 적 AI와 같은 규칙 엔진으로 통일하는 것이 낫다.
- `Game_Interpreter`의 스크립트 명령·데미지 공식 `eval` 등 임의 코드 실행 경로.

### 7.4 권장 아키텍처 스케치 (설계 제안, MV 소스 아님)
```
BattleCore (순수 TS/JS, DOM·오디오 의존 0)
  ├─ BattleState     : 양 진영 유닛, 턴, 페이즈, RNG 상태, 이벤트 플래그
  ├─ Rules           : 상수 테이블 + 데미지 파이프라인 + 특성 집계 (MV 3장 구조 차용)
  ├─ step(input)     : 입력(행동 목록) → 다음 정지 지점까지 계산 → BattleEvent[] 반환
  ├─ EnemyAI         : 행동표(조건식 + rating + 대상 규칙) (MV 4장 구조 확장)
  └─ BattleScripts   : Troop page 대응(조건 + span) → "컷신 요청" 이벤트를 로그에 출력
Client
  └─ BattlePresenter : BattleEvent[]를 애니메이션/사운드/UI로 재생, 컷신은 에피소드 인터프리터로
Tool
  ├─ 데이터 에디터    : 카드/스킬/상태/적/편성/규칙 상수
  ├─ 시뮬레이터      : BattleCore를 시드별 N회 → 승률·평균 턴·데미지 분포
  └─ 리플레이 뷰어    : (seed, 입력 로그) → 이벤트 로그 재생
Server
  └─ 검증            : 같은 BattleCore로 (seed, 입력 로그) 재실행 → 결과 해시 비교
```
핵심 원칙: **같은 BattleCore 코드를 클라이언트·툴·서버가 공유**하고, MV가 섞어 둔 "연출 대기"를 로직 밖으로 완전히 빼는 것.
